# Разработка и локальный запуск

Инструкции для работы с исходниками проекта. Серверные настройки и установка
на FreeBSD описаны в [руководстве администратора](deploy.md).

## Локальная разработка и база данных

Скопируйте `.env.example` в `.env` и задайте свой `DJANGO_SECRET_KEY`.
Локальный `.env` не попадает в Git. Для `make run` и `make dev`
используйте `DJANGO_DEBUG=True`: Django покажет подробные ошибки и будет
автоматически отдавать файлы статики при разработке.

Проект использует **только PostgreSQL**: `DATABASE_URL` обязателен во всех
окружениях. SQLite больше не подключается; старый `db.sqlite3` сохраняется,
но его данные не переносятся автоматически.

### Локальный PostgreSQL

Установите Python 3.12.x, uv и сервер PostgreSQL (не только клиент).
Команды `initdb`, `pg_ctl` и `postgres` должны относиться к одной установленной
версии. Скрипт ищет их в `PATH` или каталоге из `pg_config --bindir`.
При необходимости задайте `PG_BINDIR`, например `/usr/lib/postgresql/16/bin`
на Linux или `/usr/local/bin` на FreeBSD. Запускайте от обычного пользователя.

```sh
uv sync --locked
make db-start
# Скопируйте выведенный DATABASE_URL в свой .env.
make migrate
uv run python manage.py createsuperuser
make run
```

`make run` (и `make dev`) сначала запускает локальную БД, если она остановлена.
Миграции при обычном запуске не применяются автоматически: после изменения
схемы выполняйте `make migrate`. При работе с внешней БД используйте
`uv run python manage.py runserver`, чтобы не поднимать локальный кластер.

Кластер хранится в `.local/postgres/data`, журнал — `.local/postgres/server.log`,
Unix-сокет — в `.local/postgres/socket`. TCP отключён (`listen_addresses = ''`).
`make db-status` показывает состояние, `make db-stop` останавливает кластер.
Остановка Django не останавливает БД и не удаляет данные.
Каталог `.local/` исключён из Git. При перемещении проекта
остановите БД и обновите путь в `postgresql.conf` и `DATABASE_URL`.

Это **только dev-кластер**: роль `lhec_dev` является его суперпользователем,
локальная аутентификация — `trust`, но каталог и сокет доступны только владельцу
(0700). Не используйте эти настройки для production и не открывайте каталог
другим пользователям. Пароль для этого dev-подключения не требуется.

### Сброс пробных данных

```sh
make db-reset
# Для подтверждения введите lhec_dev.
uv run python manage.py createsuperuser
```

Команда удаляет и заново создаёт **только** БД `lhec_dev` в локальном кластере
этого проекта и применяет миграции. Она не использует `DATABASE_URL` из `.env`
для выбора удаляемой БД и перед удалением проверяет каталог подключённого
кластера. Администраторы и всё содержимое dev-БД будут удалены. Загруженные
файлы в `media` и закрытых каталогах остаются на диске.
Автоматического сброса при запуске сервера нет.

## Повседневная разработка

Команды выполняются из корня проекта. Для локального Makefile нужен GNU make;
на FreeBSD вызывайте его как `gmake`.

### CSS и шаблоны

Для сборки стилей установите Node.js и npm, затем зависимости из lock-файла:

```sh
npm ci
make styles
```

`make styles` собирает CSS и запускает `collectstatic`. Для одновременного
запуска Django и отслеживания изменений CSS используйте `make dev`.
`make css` только пересобирает CSS, `make tailwind` запускает его отслеживание.
Исходники и общие компоненты описаны в [дизайн-системе](design-system.md).

### Миграции

После изменения моделей создайте и проверьте миграции:

```sh
make makemigrations
make check-migrations
make migrate
make show-migrations
```

`check-migrations` проверяет соответствие моделей миграциям, а `show-migrations`
показывает состояние их применения к выбранной БД.

### Проверки и тесты

Для Django-тестов нужна PostgreSQL с правом создания тестовой БД.
Задайте отдельную БД в `DATABASE_URL` и `DJANGO_SECURE_SSL_REDIRECT=False`,
поскольку тестовый клиент использует HTTP. Перед тестами соберите статику:
часть страниц использует её манифест.

```sh
uv run python manage.py check
uv run python manage.py collectstatic --noinput
uv run python manage.py test
make check-migrations
```

Тесты упаковки можно запускать без БД и внешних сборщиков:

```sh
python3 -m unittest discover -s tests -v
```

## Переводы интерфейса

Строки интерфейса помечены `translate` / `blocktranslate` в шаблонах
и `gettext_lazy` в Python. Английский каталог: `locale/en/LC_MESSAGES/django.po`.
Для обновления переводов установите системный GNU gettext (`apt install gettext`),
выполните `make messages`, заполните `msgstr` в каталоге и запустите
`make compilemessages`. Файл `django.mo` включён в репозиторий для локального
запуска; после изменения каталога обновляйте его вместе с `.po`.
Перезапустите сервер после обновления переводов.

## Зависимости и lock-файлы

Требования редактируются в `pyproject.toml`,
после чего разработчик выполняет `uv lock` и сохраняет оба файла в Git.
`uv.lock` фиксирует версии прямых и транзитивных зависимостей и условия их
выбора для разных платформ. На FreeBSD устанавливаются `psycopg` и `psycopg-c`
(эквивалент `psycopg[c]`, расширение собирается с системной `libpq`), на остальных
системах CPython — `psycopg` и `psycopg-binary` (эквивалент `psycopg[binary]`).
Три пакета Psycopg закреплены на одной версии; обновляйте их совместно.
Пакеты реализаций указаны явно: в uv 0.11.26 экспорт платформенных extras
теряет условия ОС для этих зависимостей, а явные зависимости их сохраняют.

При подготовке **каждого** релиза, локально или отдельным шагом CI, выполните:

```sh
make release-requirements
```

Команда выполняет `uv export --locked --no-dev --no-emit-project --output-file
requirements.txt`: экспортирует версии, платформенные условия и хеши из
lock-файла. При несогласованном `pyproject.toml`/`uv.lock` она завершается
ошибкой; сначала обновите lock и проверьте изменения. `requirements.txt`
сохраняется в Git и включается в поставку вместе с кодом и `Makefile.prod`.
Не редактируйте его вручную. Шаг экспорта должен завершиться успешно перед
упаковкой релиза; полный архив собирает `make release` (см. ниже).

`.python-version` выбирает Python 3.12 для локальных инструментов,
`requires-python = ">=3.12"` объявляет допустимый диапазон версий.
На сервере используйте Python **3.12.x**, как в разработке: обычные venv/pip
не выбирают интерпретатор по `.python-version`. Более новые ветки Python
требуют отдельной проверки проекта.

## Подготовка релиза у разработчика или в CI

Нужны Git, GNU make, Python 3.12, uv, Node.js с npm и GNU gettext (`msgfmt` в `PATH`),
а также доступ к источникам Python- и npm-пакетов. Используйте версии uv и Node.js,
проверенные с текущими lock-файлами. На сервере эти инструменты сборки не нужны.
Локальная БД, запущенный Django и `.env` для сборки не требуются.
Проверка самой упаковки без БД и внешних сборщиков:
`python3 -m unittest discover -s tests -v`.

Сначала обновите необходимые lock-файлы и выполните проверки проекта. Для
Django-тестов нужна настроенная PostgreSQL с правом создания тестовой БД:

```sh
uv sync --locked
uv run python manage.py collectstatic --noinput
uv run python manage.py test
make check-migrations
make release-requirements
# Проверьте изменения и сохраните все файлы релиза в Git-коммите.
git status --short
make release
```

Перед тестами задайте отдельную PostgreSQL-БД в `DATABASE_URL` и
`DJANGO_SECURE_SSL_REDIRECT=False`: тестовый клиент использует HTTP.
`collectstatic` нужен и в чистом checkout перед тестами: часть страниц использует
манифест статики. Для production-проверок восстановите серверные HTTPS-настройки.

`make release` запускается из корня проекта и требует чистого рабочего дерева,
включая отсутствие неотслеживаемых файлов, не скрытых `.gitignore`.
Он упаковывает именно `HEAD`: незакоммиченные изменения не допускаются.
Команда сама повторно экспортирует зависимости, так что отдельный
`make release-requirements` не заменяет сборку и при обычной повторной сборке
того же коммита не обязателен.

Сборка во временном каталоге выполняет по порядку:

1. Получение снимка `HEAD` через `git archive` без истории и каталога `.git`.
2. `uv sync --locked --no-dev` и экспорт `requirements.txt` с хешами из lock-файла.
3. `npm ci` и `npm run css:build`.
4. Повторную компиляцию `.po` в `.mo` через `django-admin compilemessages`.
5. Отбор файлов, проверку обязательных ресурсов, упаковку и вычисление SHA-256.

Весь порядок задаёт `Makefile`: цель `release` создаёт временный снимок,
запускает в нём `release-prepare` и только после её успешного завершения вызывает
Python-упаковщик. `release-prepare` последовательно выполняет `uv sync`,
`release-requirements`, `release-css` и `release-translations`, в том числе при
`make -j release`. `release-css` устанавливает npm-зависимости и вызывает общую
цель `css`, которую также использует локальная `styles`.
`release-translations` удаляет прежние `.mo` во временном снимке и компилирует
каталоги заново без загрузки настроек Django. Python отвечает только за отбор
и проверку подготовленных файлов, метаданные, архив и контрольную сумму.

Для выпуска достаточно **одной команды `make release`**. Внутренние цели
`release-prepare`, `release-css`, `release-translations` не требуется запускать
в рабочем дереве: они изменяют файлы того каталога, из которого вызваны.
Для локальной сборки CSS без `collectstatic` есть `make css` (после `npm ci`);
`make styles` дополнительно выполняет `collectstatic` с локальными настройками.
На FreeBSD для сборки используйте GNU make (`gmake release`); `Makefile.prod`
по-прежнему работает с системным make FreeBSD.

Ошибка любого шага прерывает выпуск. Исходники, локальные зависимости и данные
в рабочем каталоге не меняются. Результаты находятся в `dist/` (исключён из Git):
`lhec-<полный-hash-коммита>.tar.gz` и одноимённый файл с суффиксом `.sha256`.
`RELEASE.json` внутри архива содержит коммит, время коммита и список файлов.
Повторная сборка того же коммита заменяет результаты; побайтовая идентичность
архивов не гарантируется, контрольную сумму передавайте вместе с конкретным архивом.

В поставку входят `manage.py`, рабочие Python-модули `config`, `core`, `education`,
`publications`, `research`, `users`, все их миграции, шаблоны и статика,
`locale` с `.po`/`.mo`, `requirements.txt`, `Makefile.prod`, `.env.example` и README.
Состав задаётся разрешённым списком; при добавлении новых приложений или ресурсов
других типов обновите `scripts/build_release.py`.

Не входят тесты и тестовые данные, `.git`, `.env`, `.venv`, кеши, `node_modules`,
исходники и инструменты сборки CSS, dev-Makefile, скрипты локальной БД,
`pyproject.toml`, lock-файлы, `staticfiles`, `media`, `private_publications`,
`.local` и локальные БД. `requirements.txt` — единственный источник установки
Python-зависимостей для администратора; вручную его не редактируют.
`collectstatic` выполняется на сервере после установки зависимостей, поскольку
должен включить также статику установленной Django-админки.

## API парсера библиографических файлов

`publications/importers.py` разбирает ровно одну публикацию из BibTeX или RIS.

Сам парсер не сохраняет записи,
не загружает вложения и не обращается к внешним API.

```python
from publications.importers import parse_publication, find_duplicates

result = parse_publication(uploaded_file)  # Django UploadedFile, UTF-8, до 2 МБ
# Либо parse_publication(text_or_bytes, format='bibtex') / format='ris'.
initial = result.data             # Значения полей Publication для формы
errors = result.errors           # Ошибки полей, которые нужно исправить
warnings = result.warnings       # Неизвестный тип и неперенесённые поля
unmapped = result.unmapped_fields  # Неперенесённые поля с исходными значениями
matches = find_duplicates(result)  # DuplicateMatch(publication, reason)
```

Пустой, повреждённый файл или несколько записей вызывают
`PublicationImportError`. Недостающие обязательные значения остаются в
`result.errors`: форму можно заполнить вручную. Неизвестный тип заменяется
на «Другое» с предупреждением. Публикация всегда предлагается как черновик.

Поиск дублей сравнивает нормализованный DOI, а при отсутствии DOI во входных
данных — название без различий регистра, пробелов и пунктуации вместе с годом.
Он включает неопубликованные карточки. Для редактирования можно передать
`exclude_pk`, для ограничения области поиска — `queryset`. Это кандидаты для
проверки человеком; записи не изменяются. При подключении к админке проверку
следует выполнять и перед сохранением.

Тесты: `uv run python manage.py test publications`.
