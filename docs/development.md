## Локальная разработка и база данных

Настройки:

- `.env` на основе `.env.example` (исключён из Git).
- `DJANGO_SECRET_KEY`.
- `DJANGO_DEBUG=True` для `make run` и `make dev`.
- `DATABASE_URL` с подключением к MySQL; значение окружения имеет приоритет над `.env`.

### Локальный MySQL

На Ubuntu нужны MySQL >= 8.0.16 (локально проверен 8.0.46), Python 3.12,
uv, GNU make и зависимости сборки mysqlclient:

```sh
sudo apt install mysql-server default-libmysqlclient-dev build-essential pkg-config python3-dev
uv sync --locked
make db-start
```

`db-start` явно выполняет `sudo systemctl start mysql.service`. Подготовку
учётной записи один раз выполняет администратор через `sudo mysql`.
Пример SQL (замените пароль своим, не сохраняйте его в Git):

```sql
CREATE USER 'lhec_dev'@'localhost' IDENTIFIED BY 'replace-with-local-password';
GRANT ALL PRIVILEGES ON `lhecdev`.* TO 'lhec_dev'@'localhost';
GRANT ALL PRIVILEGES ON `test\_lhecdev`.* TO 'lhec_dev'@'localhost';
```

Здесь права ограничены двумя точными именами БД, без глобальных привилегий
и GRANT OPTION. Экранирование `_` в имени тестовой БД предотвращает
совпадение с другими именами. Если пользователь уже существует, CREATE USER
не нужен; смена его пароля не входит в работу dev-скрипта.

В `.env` задайте (спецсимволы пароля кодируются для URL):

```dotenv
DATABASE_URL=mysql://lhec_dev:replace-with-local-password@%2Frun%2Fmysqld%2Fmysqld.sock/lhecdev
```

Это Unix-сокет `/run/mysqld/mysqld.sock`; путь в host закодирован для URL.
Допускаются также `localhost` (тот же Unix-сокет) и TCP через `127.0.0.1:3306`
или `[::1]:3306`. Для проверки фактического транспорта:

```sh
uv run python manage.py shell -c "from django.db import connection; connection.ensure_connection(); print(connection.connection.get_host_info())"
```

Для сокета ожидается `Localhost via UNIX socket`.

Если TCP работает, а сокет возвращает 1045, проверьте учётную запись:
`lhec_dev@127.0.0.1` и `lhec_dev@localhost` — разные записи MySQL.
Для сокета администратор должен подготовить `lhec_dev@localhost` с паролем
из `.env` и правами на `lhecdev` и `test\_lhecdev`, как в SQL выше.

Команды dev-скрипта запрещают другие имена БД, пользователей, порты,
удалённые серверы и дополнительные параметры URL. Django может использовать
другие подключения; эти ограничения относятся только к dev-скрипту.

```sh
make db-prepare
make db-check
make check-mysql
make migrate
uv run python manage.py createsuperuser
make run
```

`db-prepare` создаёт только `lhecdev`, если она отсутствует, с utf8mb4 и
utf8mb4_0900_ai_ci; существующая БД не изменяется. Скрипт не создаёт пользователей,
не выдаёт права и не меняет глобальные настройки. `db-check` проверяет подключение,
`check-mysql` — совместимость конфигурации приложения. `db-status` показывает
состояние общей службы и проверяет подключение; ошибка подключения даёт ненулевой код.

`make run` и `make dev` выполняют диагностику, затем запускают приложение;
они не запускают службу, не создают БД и не применяют миграции автоматически.
Django-тесты используют отдельную `test_lhecdev`; не задавайте для тестов имя
существующей рабочей БД и не подтверждайте удаление посторонней БД.

`make db-stop` после ввода `mysql` останавливает **общую** системную службу,
включая подключения других приложений. Остановка Django службу не останавливает.
В окружении без systemd службу нужно запускать средствами этого окружения.

### Сброс пробных данных

```sh
make db-reset
```

Команда проверяет локальный адрес, фиксированные имя БД и пользователя,
а также фактические DATABASE() и CURRENT_USER(). Затем требует ввод `lhecdev`,
удаляет и пересоздаёт только эту БД и применяет миграции с явно закреплённым
подключением. Отсутствующая БД сначала создаётся через `make db-prepare`.
Сброс не включает тестовую БД, файлы media и закрытые файлы на диске.
DDL MySQL не откатывается целиком: при ошибке миграций БД может остаться
частично заполненной; устраните причину и повторите миграции или явный сброс.

### Миграции

Требования:

- Доступ к БД из `DATABASE_URL` с правами изменения схемы.

После изменения моделей создайте и проверьте миграции:

```sh
make makemigrations
make check-migrations
make migrate
make show-migrations
```

#### Начальные миграции для первого деплоя

История миграций приложений пересобрана для пустой MySQL-БД: по одной
`0001_initial` для `core`, `users`, `education`, `research`, `publications`.
Они сразу включают актуальные поля, индексы, GeneratedField, CHECK и collation.
Миграции данных сохранены отдельно: `users/0002_create_employee_role`
создаёт группу «Сотрудники» с правом просмотра внутренних материалов,
`education/0002_seed_student_work_topics` добавляет 40 исходных тем работ.
`core/0002_auth_user_collations` задаёт правила сравнения стандартной auth.User.
Миграции Django (`auth`, `contenttypes`, `admin`, `sessions`) не изменялись.

Новая история не совместима со старой: нет squash/replaces, переноса данных
из PostgreSQL или поддержки обновления старой схемы. Не применяйте её поверх
существующей БД и не используйте `--fake-initial` для обхода различий. Для
локальной БД со старой историей нужна пустая выделенная dev-БД; тестовый
сервер Django создаёт отдельную БД автоматически. Сохранение тестовых данных
для этой пересборки не требуется по решению владельца проекта.

Проверка пересобранной истории на MySQL 8.0.46 / Django 5.2.17:

- Полный запуск на пустой тестовой БД: **192 теста, OK**.
- `tests.test_initial_migrations` и `tests.test_mysql_schema` с
  `config.test_mysql_schema_settings`: **4 теста, OK** (БД с latin1 и
  сессионным MyISAM; таблицы приложения всё равно InnoDB / utf8mb4 / DYNAMIC).
- `makemigrations --check --dry-run`: изменений нет; `migrate --check`: все
  миграции применены.
- Локальные таблицы dev-БД с тестовыми данными пересозданы; `make migrate`
  выполнил диагностику и установку с нуля. Подтверждены 40 тем, группа и право
  доступа. Старые тестовые пользователи удалены, суперпользователь не создавался.

#### Создание таблиц MySQL: InnoDB и utf8mb4

MySQL — СУБД, а InnoDB — её движок хранения таблиц: он обеспечивает
транзакции, блокировки строк и внешние ключи. `utf8mb4` — полноценный UTF-8
в MySQL, поддерживающий до четырёх байт на символ, включая emoji.
Кодировка определяет набор хранимых символов, collation — правила их сравнения.
См. [движки MySQL](https://dev.mysql.com/doc/refman/8.0/en/storage-engines.html)
и [utf8mb4](https://dev.mysql.com/doc/refman/8.0/en/charset-unicode-utf8mb4.html).

`DATABASE_URL` по-прежнему использует `mysql://`. Настройки направляют
подключение через `config.db.mysql` — небольшое расширение штатного backend
Django. Его schema editor сохраняет штатное создание столбцов, индексов,
ограничений и отложенных внешних ключей, но дополняет каждый `CREATE TABLE`:

```sql
ENGINE=InnoDB DEFAULT CHARSET=utf8mb4
COLLATE=utf8mb4_0900_ai_ci ROW_FORMAT=DYNAMIC
```

Это действует с первой операции миграций: для собственных таблиц приложения,
стандартных `auth`/`contenttypes`/`admin`/`sessions`, автоматически создаваемых
M2M-таблиц и служебной `django_migrations`. Отдельная поздняя миграция
`ALTER TABLE` для первоначального выбора движка не нужна: таблицы и внешние
ключи сразу создаются совместимыми. Формат DYNAMIC закреплён для бюджета
длинных индексов, описанного ниже. Настройки БД/сервера по умолчанию не влияют
на эти параметры новых таблиц.

Табличная collation `utf8mb4_0900_ai_ci` служит явным базовым правилом для
остального текста; специальные `db_collation` полей логинов, ФИО, slug и URL
сохраняют приоритет и описаны в разделе о сравнении строк.

Соединение использует `utf8mb4` и сессионный `default_storage_engine=InnoDB`.
SQL-режимы `STRICT_TRANS_TABLES` и `NO_ENGINE_SUBSTITUTION` добавляются к уже
действующим, остальные сохраняются. Второй запрещает молчаливую замену
недоступного движка. Глобальные параметры сервера не меняются.

Администратор предоставляет пустую БД и учётную запись с правами для миграций;
создавать таблицы, индексы или связи вручную не требуется. Сервер должен
предоставлять InnoDB, используемые collation и достаточный бюджет индексов
(локально проверены страницы InnoDB 16384 байта). Если сервер запрещает
необходимые DDL или сессионные настройки, потребуется согласование политики.

Проверка 14 ноября 2026 года на MySQL 8.0.46 / Django 5.2.17:

- В отдельной тестовой БД с `latin1` / `latin1_swedish_ci` и сессионным
  `default_storage_engine=MyISAM` весь граф миграций выполнен с нуля.
- Все **32 таблицы**, включая служебную и автоматические M2M, созданы как
  InnoDB / utf8mb4 / DYNAMIC; проверены все **30 внешних ключей**, определения
  уникальных ограничений и индексов, CHECK и работа вычисляемых полей.
- Кириллица и emoji сохраняются в собственных и стандартных моделях Django;
  M2M-связи работают, ссылка на несуществующую группу отклоняется БД.
- Проверено добавление обязательных SQL-режимов при сохранении существующего
  `ANSI_QUOTES`. Два специальных теста прошли; полный обычный набор —
  **182 теста, OK**. Глобальные настройки и основная БД не изменялись.

Воспроизведение проверки с отличающимися значениями по умолчанию:

```sh
uv run python manage.py test tests.test_mysql_schema --settings=config.test_mysql_schema_settings --noinput
```

Специальный модуль настроек предназначен только для теста: он задаёт latin1

Уже существующие таблицы новый backend автоматически не конвертирует.
Чтение метаданных локальной dev-БД подтвердило InnoDB / utf8mb4 / DYNAMIC

#### Индексы MySQL и длина URL научного профиля

Научный профиль сотрудника допускает URL до 500 символов. Модель и форма
редактирования используют один лимит; уникальность пары «сотрудник — URL»
обеспечивает обычный составной индекс.

В новой начальной миграции `users/0001_initial` поле URL сразу имеет длину
500 символов и collation `utf8mb4_0900_bin`. Промежуточная схема с длиной
2000 и исправляющая миграция для старых установок удалены: первый деплой
выполняется на пустую MySQL-БД.

Проверка индексов моделей 13 ноября 2026 года охватила 82 определения:
первичные ключи, одиночные индексы, уникальные ограничения и составные индексы,
включая стандартные модели Django и автоматически созданные M2M-таблицы.
Расчёт для utf8mb4 использует до четырёх байт на символ и размер числовых ключей.

| Индекс | Максимальный размер ключа |
| --- | ---: |
| Проект — ФИО — организация внешнего участника | `(255 + 500) × 4 + 8 = 3028` байт |
| Сотрудник — URL научного профиля | `500 × 4 + 8 = 2008` байт |
| Slug длиной 255 символов | `255 × 4 = 1020` байт |
| Остальные индексы | не более 800 байт |

Все определения укладываются в предел 3072 байта. Проверенная локальная
конфигурация: MySQL 8.0.46, InnoDB, страницы 16384 байта, формат строк DYNAMIC.
Страницы меньшего размера и форматы строк с меньшим бюджетом индекса не покрыты
этим расчётом. См. [ограничения InnoDB](https://dev.mysql.com/doc/refman/8.0/en/innodb-limits.html).
Неиндексируемые внешние URL в других моделях ради этого лимита не сокращаются.

### Правила сравнения строк в MySQL

Для перечисленных ниже полей collation задана явно на уровне столбцов.
Настройки сервера, БД и соединения по умолчанию не определяют их сравнение.

| Данные | Collation и правило |
| --- | --- |
| Логин стандартного `auth.User` | `utf8mb4_0900_as_ci`: `Admin` и `admin` — один логин; `Семенов` и `Семёнов`, `resume` и `résumé` — разные |
| Slug направлений, проектов, лабораторных работ и курсов | `utf8mb4_0900_as_ci`: уникальность без учёта регистра; приложение сохраняет ASCII slug в нижнем регистре |
| ФИО карточек участников, внешние ФИО/организации (RU/EN), автор диссертации (RU/EN) | `utf8mb4_0900_as_ci`: регистр не учитывается, е/ё и диакритика различаются; написание сохраняется |
| Имена/фамилии стандартного `auth.User`, названия направлений и проектов (RU/EN) | `utf8mb4_0900_as_ci`: те же правила сравнения и сортировки |
| Все URL-поля | `utf8mb4_0900_bin`: точное сравнение, включая регистр пути и параметров |

Сортировка текста использует Unicode Collation Algorithm 9.0, без отдельной
локали соединения для русского или английского языка. В смешанном списке
латиница идёт перед кириллицей; проверенные последовательности:
`Adams, Baker, Clark` и `Абрамов, Белов, Семенов, Семёнов, Яковлев`.
Регистр не задаёт порядок равных строк; для устойчивой сортировки нужен
дополнительный ключ `pk` (он уже используется в списке участников).
`icontains` по ФИО также различает е/ё и диакритику. Для карточек сотрудников
однофамильцы разрешены; уникальность внешнего участника действует в пределах
проекта по паре «ФИО — организация», независимо от перевода EN.

`NormalizedNameField` приводит ФИО и организации к NFC и удаляет только
внешние пробелы; внутренние пробелы и исходный регистр сохраняются.
`CanonicalSlugField` удаляет внешние пробелы и приводит slug к нижнему
регистру. Нормализация выполняется при валидации модели, сохранении и подготовке
обычных строковых значений ORM, включая `bulk_create`, `update`, `bulk_update`.
SQL-выражения и прямой SQL могут обходить Python-нормализацию; сравнение
и уникальные индексы БД продолжают действовать. Существующие значения
миграции массово не переписывают: нормализация применяется при последующих
записях через приложение.

Логины сохраняют регистр. Для них используется стандартная нормализация
Django NFKC при создании через `create_user`/`createsuperuser` и в формах;
форма входа также использует стандартный `UsernameField`. Например, полноширинные
латинские буквы приводятся к обычным. Прямое создание стандартного `User`
через `objects.create`/`bulk_create` не вызывает NFKC, как и в обычном Django;
уникальность логина без учёта регистра всё равно защищена индексом БД.

Inline-форма участников проверяет совпадения ещё не сохранённых строк
средствами MySQL с той же collation, что и уникальный индекс. Python
`casefold()` не используется как замена правилам сравнения MySQL.

#### URL

Все URL-поля приложения явно используют `db_collation='utf8mb4_0900_bin'`:
сравнение и уникальность учитывают регистр пути и параметров запроса.
Например, `/Profile?id=AbC`, `/profile?id=AbC` и `/Profile?id=abc` — разные
сохранённые ссылки. Ссылки не приводятся целиком к нижнему регистру.
Форма научных профилей удаляет внешние пробелы и точные повторы; регистр
сохраняется. Сравнение всего сохранённого URL точное: эквивалентность разных
написаний домена, percent-encoding и порядка параметров не устанавливается.

#### Совместимость и миграции

Для выбранного набора collation требуется MySQL не ниже **8.0.17**:
`utf8mb4_0900_as_ci` существует с 8.0.2, `utf8mb4_0900_bin` — с 8.0.17.
Обе имеют `NO PAD`: конечные пробелы в прямой SQL-записи значимы.
Это нижняя граница доступности collation, а не обещание проверки всех версий:
проверенная конфигурация — **MySQL 8.0.46, Django 5.2.17** на Ubuntu.
MariaDB и FreeBSD Jail этим результатом не покрыты.

### Даты и часовые пояса

`USE_TZ=True`, `TIME_ZONE=Europe/Moscow`. Для соединения с БД параметр
`TIME_ZONE` не задан: Django использует UTC. MySQL хранит значения
`DateTimeField` в столбцах `DATETIME` без часового пояса; Django переводит
aware datetime в UTC перед записью и возвращает aware datetime в UTC при чтении.
В Python используйте `timezone.now()`, а для локальной даты —
`timezone.localdate()`. Формы админки принимают московское время, шаблоны
локализуют даты средствами Django в Python.

Текущие запросы приложения не требуют timezone-таблиц MySQL. Публикация
объявлений сравнивает UTC-моменты. Штатный фильтр дат админки Django 5.2
вычисляет локальные границы в Python и использует диапазоны `>=` / `<`;
счётчики фильтра также обходятся без SQL-преобразования часовых поясов.
При добавлении выборки по локальному дню вычисляйте начало дня и начало
следующего дня в Python и передавайте aware datetime в диапазон фильтра.
Операции `__date`, извлечение частей datetime, `Trunc`, `dates()`,
`datetimes()` и `date_hierarchy` могут добавить `CONVERT_TZ` в SQL;
их использование требует отдельной проверки.

Проверено на MySQL 8.0.46, где
`CONVERT_TZ('2026-01-01 00:00:00', 'UTC', 'Europe/Moscow')` возвращает `NULL`:
загрузка именованных часовых поясов для проверенного функционала не требуется.
Тесты проверяют сырое UTC-значение в БД, чтение, ввод через форму админки,
фильтры дат со счётчиками на границах дня, месяца и года, момент публикации
и локализованный HTML. SQL запросов страниц и фильтров проверяется на
отсутствие `CONVERT_TZ`. Существующие данные и настройки сервера не менялись;
исторические значения с неизвестным источником эти проверки не удостоверяют.

```sh
uv run python manage.py test tests.test_datetimes core research --noinput
```

Результат: **68 тестов, OK**. Использовалась отдельная тестовая БД Django,
созданная миграциями и удалённая после запуска.

## Зависимости и lock-файлы

Требования:

- uv и доступ к источникам Python-пакетов.
- GNU make для экспорта `requirements.txt`.

Требования редактируются в `pyproject.toml`,
после чего разработчик выполняет `uv lock` и сохраняет оба файла в Git.
`uv.lock` фиксирует версии прямых и транзитивных зависимостей и условия их
выбора для разных платформ. На FreeBSD устанавливаются `psycopg` и `psycopg-c`
(эквивалент `psycopg[c]`, расширение собирается с системной `libpq`), на остальных
системах CPython — `psycopg` и `psycopg-binary` (`psycopg[binary]`).
Три пакета Psycopg закреплены на одной версии; обновляйте их совместно.
Пакеты реализаций указаны явно: в uv 0.11.26 экспорт платформенных extras
теряет условия ОС для этих зависимостей, а явные зависимости их сохраняют.

При подготовке **каждого** релиза, локально или отдельным шагом CI, выполните:

```sh
make release-requirements
```

Команда выполняет `uv export --locked --no-dev --no-emit-project --output-file
requirements.txt`: экспортирует версии, платформенные условия и хеши из
lock-файла. При несогласованном `pyproject.toml`/`uv.lock` она завершается
ошибкой; сначала обновите lock и проверьте изменения. `requirements.txt`
сохраняется в Git и включается в поставку вместе с кодом и `Makefile.prod`.
Полный архив собирает `make release` (см. ниже).

## Подготовка релиза у разработчика или в CI

Требования к сборке:

- Git, GNU make, Python 3.12, uv, Node.js и npm.
- GNU gettext (`msgfmt` в `PATH`).
- Доступ к источникам Python- и npm-пакетов.
- Рабочий каталог — корень проекта.
- Чистое рабочее дерево при запуске `make release`, включая неотслеживаемые
  файлы, не скрытые `.gitignore`.

Локальная БД, запущенный Django и `.env` для сборки не требуются.
Перед новым выпуском вручную задайте `project.version` в `pyproject.toml`
в формате `X.Y.Z` (сейчас `0.1.0`). Это единственный источник версии релиза;
версия в `package.json` относится к инструментам сборки CSS и на архив не влияет.
Для повторной сборки того же выпуска номер менять не нужно.

Используем нумерацию по мотивам [SemVer](https://semver.org/):
исправления — `0.1.0` → `0.1.1`, новая функциональность — `0.1.1` → `0.2.0`.
После перехода на `1.0.0` несовместимые изменения повышают первую цифру,
совместимые возможности — вторую, исправления — третью; младшие цифры сбрасываются.
Версии `0.x.y` предназначены для начальной разработки.
Уже опубликованный номер не используйте для другого выпуска.
Упаковщик проверяет формат, но не историю опубликованных версий.

Обновите необходимые lock-файлы (`uv lock` после изменения версии), установите зависимости командой
`uv sync --locked` и выполните проверки проекта, включая тесты упаковки,
по разделу [«Проверки и тесты»](#проверки-и-тесты). Затем подготовьте релиз:

```sh
make release-requirements
```

Сохраните изменения релиза, включая версию и `uv.lock`, в Git-коммите.
Для опубликованного выпуска рекомендуется Git-тег `vX.Y.Z` на этом коммите
(например, `git tag -a v0.1.0 -m "Release 0.1.0"`). Сборка читает версию из
`pyproject.toml` в `HEAD`, а не из тега. Проверка рабочего дерева и сборка:

```sh
git status --short
make release
```

`make release` упаковывает `HEAD`.
Команда сама повторно экспортирует зависимости, так что отдельный
`make release-requirements` не заменяет сборку и при обычной повторной сборке
того же коммита не обязателен.

Сборка во временном каталоге выполняет по порядку:

1. Получение снимка `HEAD` через `git archive` без истории и каталога `.git`.
2. `uv sync --locked --no-dev` и экспорт `requirements.txt` с хешами из lock-файла.
3. `npm ci` и `npm run css:build`.
4. Повторную компиляцию `.po` в `.mo` через `django-admin compilemessages`.
5. Отбор файлов, проверку обязательных ресурсов, упаковку и вычисление SHA-256.

Весь порядок задаёт `Makefile`: цель `release` создаёт временный снимок,
запускает в нём `release-prepare` и только после её успешного завершения вызывает
Python-упаковщик. `release-prepare` последовательно выполняет `uv sync`,
`release-requirements`, `release-css` и `release-translations`, в том числе при
`make -j release`. `release-css` устанавливает npm-зависимости и вызывает общую
цель `css`, которую также использует локальная `styles`.
`release-translations` удаляет прежние `.mo` во временном снимке и компилирует
каталоги заново без загрузки настроек Django. Python отвечает только за отбор
и проверку подготовленных файлов, метаданные, архив и контрольную сумму.

Внутренние цели `release-prepare`, `release-css`, `release-translations`
изменяют файлы каталога, из которого вызваны; `make release` выполняет их
во временном снимке. Серверный `Makefile.prod` рассчитан на системный make FreeBSD.

Ошибка любого шага прерывает выпуск. Исходники, локальные зависимости и данные
в рабочем каталоге не меняются. Результаты находятся в `dist/` (исключён из Git):
`lhec-<версия>-<полный-hash-коммита>.tar.gz` и одноимённый файл с суффиксом `.sha256`.
`RELEASE.json` внутри архива содержит версию, коммит, время коммита и список файлов.
Повторная сборка того же коммита заменяет результаты; побайтовая идентичность
архивов не гарантируется.

В поставку входят `manage.py`, рабочие Python-модули `config`, `core`, `education`,
`publications`, `research`, `users`, все их миграции, шаблоны и статика,
`locale` с `.po`/`.mo`, `requirements.txt`, `Makefile.prod` и `.env.example`.
Состав задаётся разрешённым списком; при добавлении новых приложений или ресурсов
других типов обновите `scripts/build_release.py`.

Не входят тесты и тестовые данные, `.git`, `.env`, `.venv`, кеши, `node_modules`,
исходники и инструменты сборки CSS, dev-Makefile, скрипты локальной БД,
`pyproject.toml`, lock-файлы, `staticfiles`, `media`, `private_publications`,
`.local` и локальные БД. `requirements.txt` — единственный источник установки
Python-зависимостей для администратора.
`collectstatic` выполняется на сервере после установки зависимостей, поскольку
должен включить также статику установленной Django-админки.

## API парсера библиографических файлов

Требования:

- Python-зависимости проекта.
- Для `find_duplicates` — настроенное окружение Django и доступ к БД.
- Входной файл BibTeX или RIS в UTF-8, до 2 МБ, с одной публикацией.

`publications/importers.py` разбирает ровно одну публикацию из BibTeX или RIS.

Сам парсер не сохраняет записи,
не загружает вложения и не обращается к внешним API.

Пример для Python-кода приложения; `uploaded_file` — Django `UploadedFile`.
Для текста или байтов формат передаётся явно: `format='bibtex'` или `format='ris'`.

```python
from publications.importers import parse_publication, find_duplicates

result = parse_publication(uploaded_file)
initial = result.data
errors = result.errors
warnings = result.warnings
unmapped = result.unmapped_fields
matches = find_duplicates(result)
```

`data` содержит значения полей `Publication` для формы, `errors` — ошибки полей,
`warnings` — предупреждения о неизвестном типе и неперенесённых полях,
`unmapped_fields` — эти поля с исходными значениями. Поиск дублей возвращает
`DuplicateMatch(publication, reason)`.

Пустой, повреждённый файл или несколько записей вызывают
`PublicationImportError`. Недостающие обязательные значения остаются в
`result.errors`: форму можно заполнить вручную. Неизвестный тип заменяется
на «Другое» с предупреждением. Публикация всегда предлагается как черновик.

Поиск дублей сравнивает нормализованный DOI, а при отсутствии DOI во входных
данных — название без различий регистра, пробелов и пунктуации вместе с годом.
Он включает неопубликованные карточки. Для редактирования можно передать
`exclude_pk`, для ограничения области поиска — `queryset`. Это кандидаты для
проверки человеком; записи не изменяются.

Тесты парсера (настройки — в разделе [«Проверки и тесты»](#проверки-и-тесты)):

```sh
uv run python manage.py test publications
```
