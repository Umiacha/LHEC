# Развёртывание в FreeBSD Jail

Инструкция описывает установку готового релиза и подключение приложения к
существующим PostgreSQL, reverse proxy и системе управления службами.
Пути, учётные записи, транспорт до upstream, TLS и сбор журналов определяются
политиками площадки. Все пути в примерах указаны внутри Jail.

Команды приложения выполняются из окончательного каталога релиза с серверным
окружением. Настройка сервиса через изменение Python-кода не предполагается.

Инструкция подготовлена по текущей кодовой базе, составу релиза и документации
зависимостей. Сквозное развёртывание по ней в FreeBSD Jail **не
проверялось**.

## Требования и состав поставки

Поставка — `lhec-<версия>-<hash>.tar.gz` и файл `.sha256` из GitHub Release.
Архив содержит код, миграции, шаблоны, готовые CSS и переводы,
`requirements.txt`, `Makefile.prod` и метаданные `RELEASE.json` с версией и коммитом релиза.
Статика собирается после установки зависимостей.

Требуются Python **3.12.x**, PostgreSQL и reverse proxy.
Git, uv и Node.js для установки и работы релиза не нужны.
[Подготовка поставки](development.md#подготовка-релиза-у-разработчика-или-в-ci) описана отдельно.

Пример установки системных зависимостей для PostgreSQL client 16:

```sh
pkg install python312 py312-pip postgresql16-client jpeg-turbo pkgconf
```

Для сборки `psycopg-c` нужны C-компилятор, заголовки Python и `libpq`,
`pg_config` в `PATH`. Для Pillow нужны JPEG (`jpeg-turbo`) и zlib.
Python и PostgreSQL client предоставляют соответствующие заголовки;
компилятор и zlib должны быть доступны из базовой системы FreeBSD.
`gettext` требуется только при повторной компиляции переводов вне готовой поставки.

Версии и хеши Python-зависимостей зафиксированы в `requirements.txt`.
Системные библиотеки и инструменты сборки pip им не фиксируются.

## Размещение приложения и постоянных данных

Каждый релиз размещается в отдельном окончательном каталоге со своим `.venv`.
Окружение создаётся на FreeBSD по этому пути; перенос готового venv и обновление
зависимостей поверх предыдущего релиза не предусмотрены.

| Настройка | Назначение | Доступ |
| --- | --- | --- |
| `STATIC_ROOT` | Результат `collectstatic`: CSS, JS, изображения интерфейса, ресурсы админки | Запись при сборке; чтение приложению и прокси |
| `MEDIA_ROOT` | Публичные загрузки: фотографии сотрудников и галерея | Чтение и запись приложению; чтение прокси |
| `PRIVATE_PUBLICATIONS_ROOT` | Вложения публикаций, лекций, диссертаций, ВКР и все файлы учебных материалов | Чтение и запись приложению; прямой доступ через прокси запрещён |

`MEDIA_ROOT` и `PRIVATE_PUBLICATIONS_ROOT` содержат пользовательские данные,
которые должны сохраняться при обновлении приложения. `STATIC_ROOT` содержит
восстанавливаемые ресурсы: `collectstatic` собирает их из установленного релиза
и его зависимостей. Приложению и веб-серверу должен быть доступен набор статики,
соответствующий запущенной версии приложения. Размещение каталогов и способ
обновления определяются на площадке.

Из загрузок веб-сервер напрямую раздаёт только содержимое `MEDIA_ROOT`.
Все файлы учебных материалов, включая общедоступные, находятся в
`PRIVATE_PUBLICATIONS_ROOT`: их выдаёт Django после проверки публикации
и прав доступа. Этот каталог не должен быть доступен через публичные маршруты
веб-сервера.

## Установка релиза

До установки подготовьте пользователя службы, БД, постоянные хранилища,
системные зависимости и конфигурацию службы и прокси по разделам ниже.
Первая установка рассчитана на пустую БД.

1. (Опционально) проверьте целостность архива: `sha256 -q lhec-<hash>.tar.gz` должен совпадать с первым
   полем поставляемого файла `.sha256`.
2. Распакуйте архив в новый окончательный каталог релиза и перейдите в него.
3. Создайте окружение и установите зависимости от пользователя установки:

   ```sh
   export PATH="/usr/local/bin:$PATH"
   cc --version
   pg_config --version
   python3.12 -m venv .venv
   .venv/bin/python -m pip install --require-hashes -r requirements.txt
   .venv/bin/python -m pip check
   .venv/bin/python -c 'import psycopg; from psycopg import pq; print(psycopg.__version__, pq.__impl__); assert pq.__impl__ == "c"'
   .venv/bin/python -c 'from PIL import features; assert features.check("jpg") and features.check("zlib")'
   ```

4. Подготовьте серверное окружение по разделу ["Конфигурация приложения"](#конфигурация-приложения).
   Команды управления должны получать те же настройки, что и служба.
5. Выполните проверки, миграции и сборку статики с правами изменения схемы БД
   и записи в `STATIC_ROOT`:

   ```sh
   make -f Makefile.prod check
   make -f Makefile.prod check-migrations
   make -f Makefile.prod migrate
   make -f Makefile.prod collectstatic
   ```

6. При первой установке создайте администратора сайта:

   ```sh
   make -f Makefile.prod create-superuser
   ```

7. Подключите релиз к службе и статику к прокси, запустите приложение и выполните
   [проверку развёртывания](#проверка-развёртывания).
8. Передайте доступ к административному интерфейсу ответственному за наполнение
   сайта контентом. Можно передать созданную учётную запись либо создать для него
   отдельную с доступом в админку.

Миграции созданы с помощью механизмов Django, поэтому укажу: первые создают схему, группу «Сотрудники» с правом просмотра внутренних учебных материалов и исходный набор тем дипломных и курсовых работ.
Уже применённые миграции повторно не выполняются: последующий `migrate`
не восстанавливает удалённые темы и не сбрасывает изменения существующих данных.
Учётная запись администратора создаётся отдельно и сохраняется в БД.

## Конфигурация приложения

Настройки передаются через окружение процесса либо `.env` в корне релиза.
Переменные процесса имеют приоритет. После изменения настроек требуется
перезапуск процессов приложения. При использовании `.env` подготовьте его на основе `.env.example`, задав значения для production по описанию ниже.

### Основные параметры

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `DJANGO_SECRET_KEY` | Нет | Обязательный ключ для криптографической подписи данных Django |
| `DJANGO_DEBUG` | `False` | `True` — для отладки сервиса; в production — `False` |
| `DJANGO_ALLOWED_HOSTS` | `localhost,127.0.0.1` | Допустимые хосты (через запятую) |
| `DATABASE_URL` | Нет | Обязательный URL именованной PostgreSQL-БД |
| `DJANGO_SERVE_STATIC` | `True` | `False`, если `/static/` обслуживает прокси; иначе статику выдаёт WhiteNoise |
| `STATIC_ROOT` | `staticfiles/` в каталоге релиза | Каталог результата `collectstatic` |
| `MEDIA_ROOT` | `media/` в каталоге релиза | Постоянное публичное хранилище |
| `PRIVATE_PUBLICATIONS_ROOT` | `private_publications/` в каталоге релиза | Постоянное закрытое хранилище |

Перед первым запуском сгенерируйте `DJANGO_SECRET_KEY`, например после установки
Python-зависимостей:

```sh
.venv/bin/python -c 'import secrets; print(secrets.token_urlsafe(64))'
```

Запишите результат в серверный `.env` или хранилище секретов, из которого
формируется окружение службы. Ключ не включается в релиз и репозиторий;
доступ к нему ограничивается службой и администраторами. Все процессы одной
установки должны использовать одинаковое значение.

При обычном обновлении ключ менять не требуется. Его можно заменить отдельно,
но без поддержки прежнего ключа перестанут приниматься подписанные им данные,
в том числе будут сброшены пользовательские сессии. Настройка резервных ключей
через окружение в текущей версии приложения не предусмотрена. Для замены
обновите секрет и перезапустите все процессы приложения.

`DJANGO_DEBUG` и `DJANGO_SERVE_STATIC` включаются строкой `True` без учёта
регистра. Для серверных файловых путей используйте абсолютные значения.

### HTTPS и доверие к прокси

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `DJANGO_SESSION_COOKIE_SECURE` | `False` | Атрибут Secure у session cookie; `True`, если пользователи обращаются к сайту по HTTPS |
| `DJANGO_CSRF_COOKIE_SECURE` | `False` | Атрибут Secure у CSRF cookie; `True`, если пользователи обращаются к сайту по HTTPS |
| `DJANGO_TRUST_PROXY_SSL_HEADER` | `False` | Определение HTTPS по `X-Forwarded-Proto: https` |
| `DJANGO_SECURE_SSL_REDIRECT` | `False` | HTTP → HTTPS на стороне Django |
| `DJANGO_SECURE_HSTS_SECONDS` | `0` | HSTS max-age на стороне Django |
| `DJANGO_SECURE_HSTS_INCLUDE_SUBDOMAINS` | `False` | HSTS includeSubDomains |
| `DJANGO_SECURE_HSTS_PRELOAD` | `False` | HSTS preload |
| `DJANGO_SILENCED_SECURITY_CHECKS` | Пусто | Исключения проверок безопасности через запятую |

Коды `security.Wxxx` обозначают встроенные проверки конфигурации Django,
выполняемые командой `check --deploy`. Их описание приведено в
[списке проверок безопасности Django 5.2](https://docs.djangoproject.com/en/5.2/ref/checks/#security).

Булевы HTTPS-параметры принимают `True`/`False` и `1`/`0` без учёта регистра;
HSTS seconds — целое число ≥ 0. Некорректное значение останавливает запуск.

Прокси передаёт исходный `Host`. При включённом доверии к
`X-Forwarded-Proto` он обязан перезаписывать клиентский заголовок по реальной
схеме соединения; upstream должен быть доступен только доверенному прокси.
При TLS termination и редиректе на стороне Django это доверие необходимо,
иначе возможен цикл перенаправлений.

Распределение HTTPS-политик согласуется с конфигурацией площадки:

| Механизм | Обеспечивает прокси | Обеспечивает Django |
| --- | --- | --- |
| HTTP → HTTPS | `DJANGO_SECURE_SSL_REDIRECT=False`; исключение `security.W008` | `DJANGO_SECURE_SSL_REDIRECT=True` |
| HSTS | `DJANGO_SECURE_HSTS_SECONDS=0`; исключение `security.W004` | Задать max-age и параметры поддоменов/preload по политике площадки |
| Secure-cookie | В обоих случаях включить соответствующие параметры Django | В обоих случаях включить соответствующие параметры Django |

Если HSTS выдаёт Django, а includeSubDomains и preload намеренно выключены,
допустимы исключения `security.W005,security.W021`. При HSTS=0 эти две проверки
не возникают. Другие коды, кроме W004/W005/W008/W021, приложение не допускает.
Исключения отражают принятую конфигурацию; проверка Django не подтверждает
выполнение политики на прокси. HSTS для статики и собственных ответов прокси
настраивается на прокси с учётом отсутствия дублирующих заголовков.

Пример окружения для схемы, где прокси обеспечивает TLS, редирект и HSTS:

```dotenv
DJANGO_DEBUG=False
DJANGO_SECRET_KEY=<secret>
DJANGO_ALLOWED_HOSTS=lhec.example.org
DATABASE_URL=postgresql://lhec:<password>@/lhec?host=/var/run/postgresql
DJANGO_SERVE_STATIC=False
STATIC_ROOT=/var/www/lhec/releases/<hash>/staticfiles
MEDIA_ROOT=/var/db/lhec/media
PRIVATE_PUBLICATIONS_ROOT=/var/db/lhec/private
DJANGO_SESSION_COOKIE_SECURE=True
DJANGO_CSRF_COOKIE_SECURE=True
DJANGO_TRUST_PROXY_SSL_HEADER=True
DJANGO_SECURE_SSL_REDIRECT=False
DJANGO_SECURE_HSTS_SECONDS=0
DJANGO_SECURE_HSTS_INCLUDE_SUBDOMAINS=False
DJANGO_SECURE_HSTS_PRELOAD=False
DJANGO_SILENCED_SECURITY_CHECKS=security.W004,security.W008
```

## Подключение PostgreSQL

Unix-сокет:

```dotenv
DATABASE_URL=postgresql://lhec:password@/lhec?host=/var/run/postgresql
```

`host` задаёт каталог сокета, совпадающий с `unix_socket_directories`,
а не файл `.s.PGSQL.5432`. Требуются доступ пользователя приложения к сокету
и соответствующее правило `local` в `pg_hba.conf`.

TCP:

```dotenv
DATABASE_URL=postgresql://lhec:password@db.example.org:5432/lhec
```

Спецсимволы в имени пользователя и пароле должны быть percent-encoded.
Роль приложения не требует superuser; роли, выполняющей миграции, нужны права
изменения схемы. В production соединения Django имеют `conn_max_age=600`
с проверкой работоспособности соединения.

При размещении PostgreSQL в той же Jail его инициализация, IPC-параметры Jail,
автозапуск и постоянное хранение данных настраиваются средствами площадки.
Команды приложения не управляют кластером PostgreSQL.

## Запуск службы и подключение reverse proxy

WSGI entry point — `config.wsgi:application`. Пример запуска с Unix-сокетом:

```sh
.venv/bin/gunicorn --bind unix:/var/run/lhec/gunicorn.sock config.wsgi:application
```

Служба задаёт пользователя, рабочий каталог релиза, окружение, число воркеров,
таймауты, права на каталог и сокет, автозапуск и перезапуск. Gunicorn работает
под управлением принятого на площадке supervisor/rc.d. Для TCP используйте
закрытый адрес upstream. Отдельной команды запуска в `Makefile.prod` нет.

Пример фрагментов существующего Nginx `server`; TLS и общие политики остаются
в конфигурации площадки. Пути должны быть видны процессу Nginx с его стороны Jail:

```nginx
location / {
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_pass http://unix:/var/run/lhec/gunicorn.sock;
}

location ^~ /static/ {
    alias /var/www/lhec/releases/<hash>/staticfiles/;
}

location ^~ /media/ {
    alias /var/db/lhec/media/;
    autoindex off;
    add_header X-Content-Type-Options nosniff;
}
```

Пример заголовка `$scheme` предполагает завершение TLS на этом Nginx.
При нескольких прокси признак HTTPS передаётся по доверенной цепочке.
Лимиты тела запроса и таймауты согласуйте с допустимыми загрузками и скачиваниями.
В приложении нет ограничения частоты попыток входа; троттлинг пользовательской
формы входа и `/admin/login/` обеспечивается инфраструктурой.

При `DJANGO_SERVE_STATIC=False` отключается раздача статики WhiteNoise,
но его компоненты используются для сборки статики и формирования ссылок на нее (`collectstatic` при каждом релизе). Публичные загрузки обслуживает прокси, закрытые — Django.

Django выводит сообщения уровней `WARNING` и выше в `stderr` с временем,
уровнем и именем логгера; исключения с информацией об ошибке содержат traceback.
Файлы журналов приложение не создаёт, почтовый обработчик ошибок отключён.
Сбор и ротация stderr, а также access/error logs Gunicorn и прокси настраиваются
средствами площадки.

## Проверка развёртывания

`make -f Makefile.prod check` выполняет `check --deploy --fail-level WARNING`:
неисключённые предупреждения блокируют проверку. Команда анализирует настройки
Django; сертификат, фактические заголовки, маршруты прокси и права файловой системы
проверяются отдельно.

Перед вводом в эксплуатацию проверьте:

- Внешний HTTP → HTTPS, сертификат и HSTS согласно принятой политике.
- Вход в `/admin/` и Secure-атрибуты session/CSRF cookie.
- Страницы сайта, переводы и статику, включая ресурсы админки.
- Загрузку и получение публичных изображений.
- Скачивание общедоступного учебного материала, отказ анонимному пользователю
  для внутреннего и доступ сотруднику с соответствующим правом.
- Отсутствие прямой публичной раздачи закрытого хранилища.
- Поступление ошибок в принятую систему журналирования.

## Обновление, резервное копирование и откат

Обновление выполняется новым архивом в отдельном каталоге:

1. Проверьте архив, установите зависимости и подготовьте окружение нового релиза.
2. Выполните `check` и `check-migrations` с серверными настройками.
3. Остановите службу и остальные источники записи в БД и хранилища загрузок.
   Подготовьте согласованную резервную копию БД, `MEDIA_ROOT` и
   `PRIVATE_PUBLICATIONS_ROOT`.
4. Выполните `migrate` и `collectstatic` из нового релиза.
5. Переключите службу и маршрут статики, запустите приложение и выполните проверки.

Генерация миграций на сервере не требуется. Эта процедура рассчитана на БД,
созданную с текущей историей миграций; переход со старой, пересозданной истории
не входит в поддерживаемый сценарий.

Резервная копия должна включать БД и оба хранилища загрузок в согласованном
состоянии. Отдельно сохраняются серверные секреты и конфигурация.
Статика восстанавливается командой `collectstatic` из соответствующего релиза.

Возврат предыдущего кода не отменяет миграции. Переключение назад допустимо
только при совместимости предыдущего релиза с полученной схемой и данными;
иначе требуется согласованное восстановление БД и файлов. Предыдущий релиз,
его окружение и статику сохраняют до завершения проверки обновления.

## Справочник эксплуатационных команд

Команды запускаются из корня релиза с серверным окружением:

| Команда | Назначение |
| --- | --- |
| `make -f Makefile.prod` | Справка |
| `make -f Makefile.prod check` | Проверки безопасности; предупреждения считаются ошибками |
| `make -f Makefile.prod check-migrations` | Проверка соответствия моделей миграциям без записи файлов |
| `make -f Makefile.prod show-migrations` | Состояние миграций |
| `make -f Makefile.prod migrate` | Применение миграций без интерактивных запросов |
| `make -f Makefile.prod collectstatic` | Сборка статики |
| `make -f Makefile.prod create-superuser` | Интерактивное создание администратора сайта |
| `make -f Makefile.prod compilemessages` | Повторная компиляция переводов; нужен gettext, для готового релиза не требуется |
| `.venv/bin/python manage.py changepassword <логин>` | Смена пароля существующего пользователя |

`Makefile.prod` совместим с системным make FreeBSD и использует
`.venv/bin/python`. Другой интерпретатор задаётся аргументом
`PYTHON=/path/to/venv/bin/python`. Все цели, кроме справки, требуют итогового
`DEBUG=False`. Зависимости автоматически не устанавливаются.
