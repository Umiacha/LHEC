# Развёртывание и сопровождение production-сервиса

Инструкция для администратора FreeBSD Jail: установка готового релиза,
настройка PostgreSQL, окружения, Gunicorn и Nginx, хранение файлов и журналов.
Команды приложения выполняются из окончательного каталога релиза от пользователя
службы, если явно не указано иное.

Подготовка архива описана в [руководстве разработчика](development.md).
Конфигурацию системной службы, TLS и проксирования администратор настраивает
в соответствии с инфраструктурой сервера.

## Сервер и Unix-сокет в Jail

Для Django Unix-сокет уже поддерживается драйвером PostgreSQL. В URL параметр
`host` задаёт **каталог** сокета, а не файл `.s.PGSQL.5432`:

```dotenv
DATABASE_URL=postgresql://lhec:password@/lhec?host=/var/run/postgresql
```

Путь приведён как пример: он должен совпадать с `unix_socket_directories`
PostgreSQL внутри Jail. Спецсимволы в логине и пароле URL необходимо кодировать
(percent-encoding). TCP остаётся доступным как альтернативный способ подключения:
`postgresql://lhec:password@127.0.0.1:5432/lhec`.

Администратор устанавливает и инициализирует production-кластер отдельно,
настраивает `sysvshm=new` для Jail, автозапуск PostgreSQL, постоянный каталог
данных и резервные копии. Для подключения через сокет он задаёт
`unix_socket_directories`, права каталога/сокета для пользователя Django
и подходящее правило `local` в `pg_hba.conf` (например, `scram-sha-256`
с паролем). При использовании только сокета можно отключить TCP через
`listen_addresses = ''`. Сокет не отменяет аутентификацию и права БД.
Production-роль Django не должна быть суперпользователем; ей нужны права на БД
и схему для применения миграций. `make db-*` на сервере не используется.

На сервере задайте `DJANGO_DEBUG=False`, `DJANGO_SECRET_KEY`, `DJANGO_ALLOWED_HOSTS`
и `DATABASE_URL` в окружении службы или серверном `.env`. Установка зависимостей
на FreeBSD описана ниже.
Миграции и сборка статики выполняются явно командами из `Makefile.prod`
(см. ниже). В релизном архиве переводы уже скомпилированы. Каталог данных БД должен сохраняться
независимо от обновления кода Django.

Перед деплоем запускайте `python manage.py check --deploy` с **серверными**
переменными окружения. Команда проверяет настройки безопасности Django и
выводит предупреждения, например о HTTPS и защищённых cookie. Обычный
`manage.py check` не включает эти дополнительные проверки. Проверка не
исправляет настройки и без `--fail-level WARNING` может завершиться успешно
даже при предупреждениях. Для автоматического блокирования деплоя по ним
используйте `python manage.py check --deploy --fail-level WARNING`, когда
настроите все нужные параметры безопасности.

## HTTPS и безопасность через окружение

Этот сервис не заточен под конкретную конфигурацию продакшен веб-сервера (или в принципе принятые на нем политики), поэтому некоторые параметры по взаимодействию посредством HTTP-протокола вынесены в .env приложения. На продакшен нужно выставить нужные значения в .env в соответствии с уже политиками веб-сервера.
TLS завершается на прокси: он предъявляет сертификат, а браузер проверяет его.
Django может получать от прокси обычный HTTP через закрытый порт или Unix-сокет.
Это не мешает приложению устанавливать атрибут `Secure` для session/CSRF cookie:
браузер отправляет такие cookie только по HTTPS. Шифрование соединения само
по себе этот атрибут не добавляет. `HttpOnly` у session cookie и `SameSite=Lax`
остаются стандартными настройками Django.

HTTPS-редирект — ответ на HTTP-запрос с перенаправлением на `https://`.
Его предпочтительно делать на прокси; Django может выполнять его дополнительно.
HSTS — заголовок `Strict-Transport-Security`, который браузер запоминает после
HTTPS-ответа и затем обращается к домену сразу по HTTPS в течение `max-age` секунд.
Он не заменяет сертификат и не защищает первое посещение до получения политики.
`includeSubDomains` распространяет политику на все поддомены; `preload` обозначает
согласие на включение в браузерный список HTTPS-доменов (само включение требует
отдельной заявки). Редирект и HSTS могут полностью обеспечиваться прокси.

Пример серверного окружения: Django ставит cookie, выполняет резервный редирект
и выдаёт HSTS; прокси завершает TLS и перенаправляет внешний HTTP:

```dotenv
DJANGO_DEBUG=False
DJANGO_ALLOWED_HOSTS=lhec.example.org
DJANGO_SESSION_COOKIE_SECURE=True
DJANGO_CSRF_COOKIE_SECURE=True
DJANGO_SECURE_SSL_REDIRECT=True
DJANGO_TRUST_PROXY_SSL_HEADER=True
DJANGO_SECURE_HSTS_SECONDS=300
DJANGO_SECURE_HSTS_INCLUDE_SUBDOMAINS=False
DJANGO_SECURE_HSTS_PRELOAD=False
DJANGO_SILENCED_SECURITY_CHECKS=security.W005,security.W021
```

Также обязательны настоящие `DATABASE_URL` и случайный `DJANGO_SECRET_KEY`.
Булевы параметры этого раздела принимают True/False или 1/0 (без учёта регистра),
HSTS seconds — целое число >= 0; некорректное значение останавливает запуск.
По умолчанию cookie Secure, редирект и доверие к прокси выключены, HSTS равен 0:
локальная разработка по HTTP продолжает работать. Изменив окружение, перезапустите
процессы Django; переменные процесса имеют приоритет над `.env`.

`DJANGO_TRUST_PROXY_SSL_HEADER=True` включает доверие к `X-Forwarded-Proto: https`.
Прокси обязан удалять/перезаписывать входящий заголовок и выставлять его по
реальной схеме клиентского соединения; доступ к Gunicorn должен быть разрешён
только прокси. Иначе клиент сможет подделать признак HTTPS. Прокси передаёт
исходный `Host`, проверяемый Django через `DJANGO_ALLOWED_HOSTS`.
Если доверие выключено при TLS на прокси и включённом редиректе Django,
возможен бесконечный редирект: Django видит внутренний HTTP даже после перехода.

Начните HSTS с 300 секунд, проверьте HTTPS и затем увеличьте срок, например до
31536000. Включайте поддомены только после проверки HTTPS на каждом из них,
preload — после отдельного решения администратора. Выключение HSTS на сервере
не отменяет уже сохранённую браузером политику немедленно.

`make -f Makefile.prod check` запускает `check --deploy --fail-level WARNING`.
Проверка анализирует настройки Django, но не проверяет сертификат, конфигурацию
прокси и реальные заголовки. Поэтому для сознательных исключений предусмотрена
`DJANGO_SILENCED_SECURITY_CHECKS` (список через запятую, по умолчанию пустой):

- `security.W005`, `security.W021`: поддомены/preload намеренно не включены,
  как в примере выше. Включать их только ради прохождения проверки не нужно.
- `security.W008`: редирект полностью обеспечивает прокси;
  тогда задайте `DJANGO_SECURE_SSL_REDIRECT=False`.
- `security.W004`: HSTS полностью обеспечивает прокси;
  тогда задайте `DJANGO_SECURE_HSTS_SECONDS=0`.

Если оба механизма находятся на прокси, задайте исключения
`security.W004,security.W008`; W005/W021 при HSTS=0 не возникают.
Прокси должен добавлять HSTS также к собственным HTTPS-ответам и статике;
избегайте дублирования заголовка. Перед исключением проверки подтвердите
внешним запросом, что HTTP перенаправляется на HTTPS, а HTTPS-ответ содержит
ожидаемый `Strict-Transport-Security`. Cookie Secure остаются обязанностью
Django при любой из схем. Другие предупреждения этой переменной скрыть нельзя.

См. [SecurityMiddleware](https://docs.djangoproject.com/en/5.2/ref/middleware/#security-middleware)
и [доверие к прокси](https://docs.djangoproject.com/en/5.2/ref/settings/#secure-proxy-ssl-header).

## Зависимости релиза и установка на FreeBSD

На сервере **uv не требуется**. Используйте Python **3.12.x**, как в разработке.
На FreeBSD устанавливаются `psycopg` и `psycopg-c` с системной `libpq`.
Зависимости устанавливаются из готового `requirements.txt`; подготовка этого
файла описана в [руководстве разработчика](development.md#зависимости-и-lock-файлы).

Администратор устанавливает системные зависимости **внутри Jail**, где
собирается и запускается приложение. Например, для PostgreSQL client 16
(команда от root; версию клиента согласуйте с принятой конфигурацией сервера):

```sh
pkg install python312 py312-pip postgresql16-client jpeg-turbo pkgconf
```

Для сборки `psycopg-c` нужны C-компилятор (`cc`/Clang), заголовки Python и
`libpq`, а также `pg_config` в `PATH`. Пакеты Python и PostgreSQL client
предоставляют соответствующие заголовки; проверьте наличие инструментов
базовой системы FreeBSD в Jail. Для Pillow нужны заголовки и библиотеки
JPEG (`jpeg-turbo`) и zlib (базовая система FreeBSD). Дополнительные форматы
Pillow могут требовать дополнительных библиотек; установленный набор влияет
на доступные возможности. `gettext` нужен отдельно для `compilemessages`.
PostgreSQL server устанавливается отдельно, если БД размещена в этой Jail.

После установки пакетов, от пользователя приложения, из корня релиза:

```sh
export PATH="/usr/local/bin:$PATH"
cc --version
pg_config --version
python3.12 -m venv .venv
.venv/bin/python -m pip install --require-hashes -r requirements.txt
.venv/bin/python -m pip check
.venv/bin/python -c 'import psycopg; from psycopg import pq; print(psycopg.__version__, pq.__impl__); assert pq.__impl__ == "c"'
.venv/bin/python -c 'from PIL import features; assert features.check("jpg") and features.check("zlib")'
```

Создавайте `.venv` заново для каждого релиза в его окончательном каталоге;
не переносите venv с Linux и не устанавливайте обновление поверх старого
окружения. pip сам выбирает зависимости по платформенным условиям и собирает
C-расширения; прямой установки проекта через `pip install .` не требуется.
Затем подготовьте серверное окружение и выполните команды `Makefile.prod`.

Фиксируются версии и хеши Python-пакетов. Версии FreeBSD, Python 3.12.x,
системных библиотек и инструментов изолированной сборки pip Python lock-файлом
не фиксируются. Это не побитовая воспроизводимость сборки: для неё потребуется
отдельно контролировать сборочное окружение и готовить wheels на FreeBSD.
Установка на реальной FreeBSD VM и в Jail требует отдельной проверки.

Справка: [установка Psycopg](https://www.psycopg.org/psycopg3/docs/basic/install.html#local-installation),
[сборка Pillow](https://pillow.readthedocs.io/en/stable/installation/building-from-source.html),
[экспорт lock-файла uv](https://docs.astral.sh/uv/concepts/projects/sync/#exporting-the-lockfile).

## Сборка и установка релизного архива

Разработчик размещает в GitHub Release готовый `tar.gz` и его файл `.sha256`.
Клонировать Git-репозиторий на сервер не требуется. Архив содержит исходный
Python-код и готовые ресурсы приложения, но не Python-интерпретатор и зависимости.
WhiteNoise остаётся production-зависимостью: даже при отключённом middleware
его `CompressedManifestStaticFilesStorage` используется для обработки статики
и построения ссылок на неё. Загрузки пользователей WhiteNoise не обрабатывает.

### Подготовка у разработчика или в CI

См. [сборку релиза](development.md#подготовка-релиза-у-разработчика-или-в-ci).

### Установка администратором в FreeBSD Jail

До первой установки подготовьте системные зависимости из раздела выше,
PostgreSQL, пользователя службы, постоянные каталоги загрузок и настройки
Nginx/службы. При обновлении сделайте согласованную резервную копию БД и загрузок;
на время применения миграций остановите службу и другие записи в БД.

1. Передайте архив и контрольную сумму на сервер. На FreeBSD выполните
   `sha256 -q lhec-<hash>.tar.gz` и сравните результат с первым полем
   файла `.sha256`. На Linux: `sha256sum -c lhec-<hash>.tar.gz.sha256`.
   Продолжайте установку только при совпадении контрольной суммы.
2. Распакуйте архив в новый **окончательный** каталог релиза и перейдите в него.
   Не распаковывайте обновление поверх предыдущего релиза.
3. Создайте `.venv` и установите зависимости, как в разделе про FreeBSD:

   ```sh
   python3.12 -m venv .venv
   .venv/bin/python -m pip install --require-hashes -r requirements.txt
   .venv/bin/python -m pip check
   ```

4. Настройте окружение службы и команд управления либо серверный `.env`.
   Включите `DJANGO_DEBUG=False`, задайте секрет, хосты, БД и HTTPS-параметры.
   `.env.example` содержит dev-значения: не используйте его без изменений.
   При раздаче статики Nginx задайте `DJANGO_SERVE_STATIC=False`.
   `MEDIA_ROOT` и `PRIVATE_PUBLICATIONS_ROOT` должны указывать на постоянные
   каталоги вне релиза. Для каждого релиза предпочтителен отдельный `STATIC_ROOT`,
   на который при переключении направляется Nginx.
5. Из каталога релиза, от пользователя приложения и с серверным окружением:

   ```sh
   make -f Makefile.prod check
   make -f Makefile.prod check-migrations
   make -f Makefile.prod migrate
   make -f Makefile.prod collectstatic
   ```

   Предупреждения безопасности останавливают `check`; исключения настраиваются
   только после согласования с конфигурацией прокси (см. раздел HTTPS).
   Пользователю команд нужны права изменения схемы БД и записи в `STATIC_ROOT`.
   `compilemessages` не требуется: готовые `.mo` уже в архиве.
6. Только на первой установке при необходимости выполните
   `make -f Makefile.prod create-superuser`. Переключите службу на новый каталог,
   согласованно переключите статику Nginx и запустите приложение. Проверьте сайт,
   вход в админку, статику, переводы и скачивание файлов с разными правами доступа.

При наличии старых учебных файлов отдельно выполните описанный ниже перенос
до включения публичной раздачи media. Возврат старого кода сам по себе
не отменяет миграции: возможность отката зависит от совместимости схемы БД.

## Команды для production

Для серверных операций используйте отдельный `Makefile.prod` из корня проекта:

```sh
make -f Makefile.prod                  # справка, без изменений
make -f Makefile.prod check            # проверки настроек для деплоя
make -f Makefile.prod check-migrations # модели соответствуют миграциям
make -f Makefile.prod show-migrations  # состояние миграций
make -f Makefile.prod migrate          # применение миграций
make -f Makefile.prod compilemessages  # компиляция переводов
make -f Makefile.prod collectstatic    # сборка статики
make -f Makefile.prod create-superuser # интерактивное создание администратора
```

Команды используют `.venv/bin/python`, без автоматической установки зависимостей
через uv. Другой интерпретатор можно указать как
`make -f Makefile.prod check PYTHON=/path/to/venv/bin/python`.
Все операции, кроме справки, отказываются выполняться при итоговом `DEBUG=True`.
Окружение и серверный `.env` должны быть подготовлены заранее. Команда `check`
считает предупреждения безопасности ошибками; исправьте настройки до деплоя.
Проверка `DEBUG=False` не определяет, к какой именно БД вы подключаетесь:
перед миграциями проверьте серверный `DATABASE_URL` и подготовьте резервную копию.

В этом файле нет запуска dev-сервера, управления dev-БД, сброса данных,
создания миграций или тестового администратора. PostgreSQL и Gunicorn запускаются
системными службами. `create-superuser` запрашивает пароль интерактивно.
Для `compilemessages` нужен gettext. В релизном архиве CSS и переводы уже
собраны; Node.js для работы Django не требуется. После изменения каталогов
переводов вне готового релиза выполните `make -f Makefile.prod compilemessages`
и перезапустите приложение.

При подготовке архива для сервера включайте `Makefile.prod` и свежий `requirements.txt`, исключая локальный
`Makefile`, `scripts/dev_db.py`, `.local/` и локальный `.env`. Сам по себе новый
Makefile не меняет состав поставки: при Git checkout dev-файлы останутся
в репозитории. Отсутствие команд в Makefile не заменяет права пользователей ОС и БД.

## Первый администратор боевого сайта

Администратор сайта — **Django superuser**, учётная запись в базе приложения.
Она создаётся **вручную при первом деплое**: запуск Gunicorn, применение
миграций и наличие переменных `DJANGO_SUPERUSER_*` в `.env` сами по себе
администратора не создают. Успешный запуск приложения ещё не означает,
что в админку уже можно войти.

Тот, кто разворачивает сервер, должен выполнить этот шаг из корня проекта,
с тем же серверным окружением и `DATABASE_URL`, которые использует Gunicorn.
При `DJANGO_DEBUG=False` и после установки зависимостей:

```sh
make -f Makefile.prod migrate
make -f Makefile.prod create-superuser
```

Вторая команда запускает интерактивный `createsuperuser`: укажите логин,
email и собственный надёжный пароль (ввод пароля не отображается).
Это отдельная учётная запись: пользователь ОС, роль PostgreSQL и аккаунт
на сайте не заменяют её. Для выполнения команды нужны доступ к серверу
и подключение к боевой БД; знать внутреннее устройство Django не требуется.

После запуска сайта откройте `https://<домен-сайта>/admin/` и войдите
с созданными данными. Проверьте доступ к разделам наполнения контентом.
**Первый деплой считайте завершённым только после успешного входа в админку.**
Если сайт наполняет другой человек, передайте ему адрес админки и данные
входа по защищённому каналу.

При обновлении кода создавать аккаунт повторно не нужно: он сохраняется
в production-БД. Если пароль потерян, его можно сменить на сервере:

```sh
.venv/bin/python manage.py changepassword <логин>
```

Команду смены пароля также выполняйте с окружением боевого приложения.
Она не требует знания старого пароля. После смены проверьте вход в `/admin/`.

Переменные `DJANGO_SUPERUSER_USERNAME`, `DJANGO_SUPERUSER_EMAIL` и
`DJANGO_SUPERUSER_PASSWORD` из `.env.example` предназначены для локальной
команды `make create-test-admin` (`createsuperuser --noinput`). Это тестовые
данные, их нельзя использовать для боевого аккаунта. Для описанного выше
интерактивного создания production-администратора удалите эти переменные
из серверного `.env` и окружения: логин, email и пароль задаются вручную.
Изменение этих переменных не меняет пароль существующего пользователя.

## Запуск WSGI-сервера

Точка входа Django — `config.wsgi:application`. Базовая команда запуска
из корня проекта после установки зависимостей в `.venv` и подготовки
серверного `.env` или переменных окружения (см. выше):

```sh
.venv/bin/gunicorn config.wsgi:application
```

По умолчанию `DJANGO_SERVE_STATIC=True`: WhiteNoise раздаёт собранную статику
через Gunicorn, в том числе при `DJANGO_DEBUG=False`. Если на сервере `/static/`
обслуживает Nginx, задайте `DJANGO_SERVE_STATIC=False` в окружении службы
или серверном `.env` и перезапустите Gunicorn. Это отключает только
`WhiteNoiseMiddleware`; backend `CompressedManifestStaticFilesStorage`
остаётся включённым. Перед запуском и после обновления статики по-прежнему
выполняйте `collectstatic`.

Администратор настраивает адрес и порт или Unix-сокет, количество воркеров,
подключение Nginx, системную службу FreeBSD, автозапуск и перезапуск процесса.
Эти параметры задаются на сервере; отдельной команды запуска в Makefile нет.

Сервис не ограничивает частоту попыток входа в пользовательской форме и
`/admin/login/`. Настройка троттлинга на прокси — ответственность администратора.

## Логирование на сервере

Django выводит сообщения уровней `WARNING`, `ERROR` и `CRITICAL` в `stderr`
при любом значении `DJANGO_DEBUG`. Запись содержит время, уровень и имя логгера;
для исключений с переданной информацией об ошибке добавляется traceback.
Почтовый обработчик Django отключён: письма об ошибках не отправляются.
Приложение не создаёт файлы журналов. Локальный `runserver` сохраняет свой
стандартный журнал запросов.

Администратор сервера должен настроить сбор `stderr` процесса приложения,
место хранения, ограничение размера и количества архивов и ротацию журналов.
Например, можно хранить текущий файл и несколько архивов по 5–10 МБ.
Журналы веб-сервера и Gunicorn настраиваются и ротируются отдельно.

## Хранение и раздача файлов в production

Файлы разделены на три независимых каталога:

| Настройка | По умолчанию | Содержимое | Кто отдаёт |
| --- | --- | --- | --- |
| `STATIC_ROOT` | `staticfiles/` в корне проекта | Собранные CSS, JS, изображения интерфейса и статика админки | Nginx; без него настроен WhiteNoise |
| `MEDIA_ROOT` | `media/` в корне проекта | Только публичные загрузки: фотографии сотрудников и галерея | Nginx |
| `PRIVATE_PUBLICATIONS_ROOT` | `private_publications/` в корне проекта | Вложения публикаций, лекций, диссертаций, ВКР и **все** файлы `TeachingMaterial` | Django через обработчики скачивания |

У учебных материалов даже общедоступные файлы находятся в закрытом хранилище:
Django проверяет публикацию и уровень доступа при каждом скачивании. Изменение
«Для всех» на «Только для сотрудников» не требует перемещения файла. Ссылки
на файл материала строятся через `get_download_url()` или маршрут
`education:download_material`, а не через `/media/`.
HTML-шаблоны остаются частью кода приложения: Django формирует из них страницы;
Nginx не должен публиковать каталоги шаблонов.

На сервере задайте абсолютные пути в окружении службы и команд управления
или серверном `.env`, например (пути внутри Jail):

```dotenv
STATIC_ROOT=/var/www/lhec/staticfiles
MEDIA_ROOT=/var/db/lhec/media
PRIVATE_PUBLICATIONS_ROOT=/var/db/lhec/private
```

Каталоги загрузок должны сохраняться при обновлении кода. Пользователю Django
нужны чтение и запись в оба хранилища загрузок. Пользователю Nginx нужны только
чтение публичного `MEDIA_ROOT` и собранного `STATIC_ROOT`, а также проход по
родительским каталогам. Закрытое хранилище не публикуйте через `alias` или `root`.
Резервируйте БД и оба хранилища загрузок согласованно. Статика восстанавливается
сборкой: при изменении CSS разработчик выпускает новый архив через `make release`,
а администратор после установки выполняет `make -f Makefile.prod collectstatic`. Пользователю сборки нужна запись в
`STATIC_ROOT`; работающему приложению достаточно чтения этого каталога.

### Переход с прежнего хранения учебных материалов

Ранее `TeachingMaterial` сохранял файлы в `MEDIA_ROOT/education/materials/`,
в том числе внутренние материалы. **До завершения переноса не включайте прямую
раздачу `/media/`.** На время перехода остановите приложение и загрузку файлов,
сделайте резервную копию БД и каталогов. Затем:

1. Настройте постоянные хранилища. Если меняете пути, перенесите прежнее содержимое
   `media/` и `private_publications/` в соответствующие новые каталоги с сохранением
   вложенных путей. Не удаляйте прежние каталоги до проверки результата.
2. Примените `make -f Makefile.prod migrate`. Миграции схемы сами файлы
   не переносят. Упоминавшаяся ранее `education.0009` относится к прежней
   истории миграций; ограничения текущей истории описаны ниже.
3. Выполните проверку, затем перенос. `--source-root` — абсолютный путь к каталогу
   media, где сейчас находятся старые файлы учебных материалов:

   ```sh
   .venv/bin/python manage.py move_teaching_materials --source-root /var/db/lhec/media --dry-run
   .venv/bin/python manage.py move_teaching_materials --source-root /var/db/lhec/media
   ```

Команда сохраняет имена файлов и ссылки в БД, проверяет копию перед удалением
исходника и допускает повторный запуск после частичного переноса. При конфликте
содержимого или отсутствии файла в обоих каталогах она останавливается с ошибкой.
`--dry-run` не изменяет файлы. Запускайте команду без параллельных загрузок.
Она переносит только файлы, на которые ссылаются записи `TeachingMaterial`:
проверьте оставшиеся файлы в `media/education/materials/` и уберите весь этот
старый подкаталог из публичного дерева после сверки с резервной копией.
Если исходных копий media несколько, очистите все каталоги, доступные веб-серверу.
На новой установке без старых файлов этот перенос не требуется.

После проверки скачивания публичного материала, отказа анонимному посетителю
для внутреннего и доступности его сотруднику можно включить раздачу Nginx.

### Nginx

В существующий `server` добавьте (пути должны соответствовать настройкам выше
и быть видны процессу Nginx; если он вне Jail, укажите пути с его стороны):

```nginx
location ^~ /static/ {
    alias /var/www/lhec/staticfiles/;
}

# Старое место учебных материалов больше не публикуется.
location ^~ /media/education/materials/ {
    return 404;
}

location ^~ /media/ {
    alias /var/db/lhec/media/;
    autoindex off;
    add_header X-Content-Type-Options nosniff;
}
```

Nginx отдаёт весь публичный `media/` без проверки пользователя. Закрытые файлы
обслуживает Django через `FileResponse` с проверками соответствующего раздела;
прямых публичных URL для закрытого каталога нет. WhiteNoise обслуживает только
статику, а не пользовательские загрузки. Локально при `DEBUG=True` публичные
media по-прежнему отдаёт Django.


## Начальная история миграций перед первым деплоем

История миграций пересоздана для установки на пустую PostgreSQL-БД.
В каждом приложении `0001_initial` создаёт актуальную схему без промежуточных
удалений и переименований. Дополнительно применяются:

- `education.0002_seed_student_work_topics` — все 40 тем дипломных и курсовых
  работ с прежними разделами и порядком; повторный запуск не перезаписывает правки.
- `users.0002_create_employee_role` — группа «Сотрудники» и право просмотра
  внутренних учебных материалов.

Старые номера миграций в прежних описаниях изменений относятся к прежней
истории. Новая история не предназначена для обновления БД со старыми миграциями.
Для первого запуска выполните `make -f Makefile.prod migrate`, затем
`make -f Makefile.prod create-superuser`.
Перенос дипломов между приложениями, преобразование таблицы участников и снятие
`is_staff` у прежних сотрудников больше не нужны: существующих данных нет,
таблицы сразу создаются в итоговом виде, а новые роли назначаются через текущую
логику приложения.
