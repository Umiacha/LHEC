# ТЗ

## Локальная разработка и база данных

Скопируйте `.env.example` в `.env` и задайте свой `DJANGO_SECRET_KEY`.
Локальный `.env` не попадает в Git. Для `make run` и `make dev`
используйте `DJANGO_DEBUG=True`: Django покажет подробные ошибки и будет
автоматически отдавать файлы статики при разработке.

Проект использует **только PostgreSQL**: `DATABASE_URL` обязателен во всех
окружениях. SQLite больше не подключается; старый `db.sqlite3` сохраняется,
но его данные не переносятся автоматически.

### Локальный PostgreSQL

Установите Python >= 3.12, uv и сервер PostgreSQL (не только клиент).
Команды `initdb`, `pg_ctl` и `postgres` должны относиться к одной установленной
версии. Скрипт ищет их в `PATH` или каталоге из `pg_config --bindir`.
При необходимости задайте `PG_BINDIR`, например `/usr/lib/postgresql/16/bin`
на Linux или `/usr/local/bin` на FreeBSD. Запускайте от обычного пользователя.

```sh
uv sync --locked
make db-start
# Скопируйте выведенный DATABASE_URL в свой .env.
make migrate
uv run python manage.py createsuperuser
make run
```

`make run` (и `make dev`) сначала запускает локальную БД, если она остановлена.
Миграции при обычном запуске не применяются автоматически: после изменения
схемы выполняйте `make migrate`. При работе с внешней БД используйте
`uv run python manage.py runserver`, чтобы не поднимать локальный кластер.

Кластер хранится в `.local/postgres/data`, журнал — `.local/postgres/server.log`,
Unix-сокет — в `.local/postgres/socket`. TCP отключён (`listen_addresses = ''`).
`make db-status` показывает состояние, `make db-stop` останавливает кластер.
Остановка Django не останавливает БД и не удаляет данные.
Каталог `.local/` исключён из Git. При перемещении проекта
остановите БД и обновите путь в `postgresql.conf` и `DATABASE_URL`.

Это **только dev-кластер**: роль `lhec_dev` является его суперпользователем,
локальная аутентификация — `trust`, но каталог и сокет доступны только владельцу
(0700). Не используйте эти настройки для production и не открывайте каталог
другим пользователям. Пароль для этого dev-подключения не требуется.

### Сброс пробных данных

```sh
make db-reset
# Для подтверждения введите lhec_dev.
uv run python manage.py createsuperuser
```

Команда удаляет и заново создаёт **только** БД `lhec_dev` в локальном кластере
этого проекта и применяет миграции. Она не использует `DATABASE_URL` из `.env`
для выбора удаляемой БД и перед удалением проверяет каталог подключённого
кластера. Администраторы и всё содержимое dev-БД будут удалены. Загруженные
файлы в `media` и закрытых каталогах остаются на диске.
Автоматического сброса при запуске сервера нет.

### Сервер и Unix-сокет в Jail

Для Django Unix-сокет уже поддерживается драйвером PostgreSQL. В URL параметр
`host` задаёт **каталог** сокета, а не файл `.s.PGSQL.5432`:

```dotenv
DATABASE_URL=postgresql://lhec:password@/lhec?host=/var/run/postgresql
```

Путь приведён как пример: он должен совпадать с `unix_socket_directories`
PostgreSQL внутри Jail. Спецсимволы в логине и пароле URL необходимо кодировать
(percent-encoding). TCP остаётся доступным как альтернативный способ подключения:
`postgresql://lhec:password@127.0.0.1:5432/lhec`.

Администратор устанавливает и инициализирует production-кластер отдельно,
настраивает `sysvshm=new` для Jail, автозапуск PostgreSQL, постоянный каталог
данных и резервные копии. Для подключения через сокет он задаёт
`unix_socket_directories`, права каталога/сокета для пользователя Django
и подходящее правило `local` в `pg_hba.conf` (например, `scram-sha-256`
с паролем). При использовании только сокета можно отключить TCP через
`listen_addresses = ''`. Сокет не отменяет аутентификацию и права БД.
Production-роль Django не должна быть суперпользователем; ей нужны права на БД
и схему для применения миграций. `make db-*` на сервере не используется.

На сервере задайте `DJANGO_DEBUG=False`, `DJANGO_SECRET_KEY`, `DJANGO_ALLOWED_HOSTS`
и `DATABASE_URL` в окружении службы или серверном `.env`. Для FreeBSD может
потребоваться адаптация установки `psycopg[binary]`: если wheel недоступен,
используйте `psycopg[c]` со сборкой или `psycopg` с системной `libpq`;
текущая зависимость пока рассчитана на окружения с готовым binary-пакетом.
Миграции, компиляция переводов и сборка статики выполняются явно командами
из `Makefile.prod` (см. ниже). Каталог данных БД должен сохраняться
независимо от обновления кода Django.

Перед деплоем запускайте `python manage.py check --deploy` с **серверными**
переменными окружения. Команда проверяет настройки безопасности Django и
выводит предупреждения, например о HTTPS и защищённых cookie. Обычный
`manage.py check` не включает эти дополнительные проверки. Проверка не
исправляет настройки и без `--fail-level WARNING` может завершиться успешно
даже при предупреждениях. Для автоматического блокирования деплоя по ним
используйте `python manage.py check --deploy --fail-level WARNING`, когда
настроите все нужные параметры безопасности.

### Команды для production

Для серверных операций используйте отдельный `Makefile.prod` из корня проекта:

```sh
make -f Makefile.prod                  # справка, без изменений
make -f Makefile.prod check            # проверки настроек для деплоя
make -f Makefile.prod check-migrations # модели соответствуют миграциям
make -f Makefile.prod show-migrations  # состояние миграций
make -f Makefile.prod migrate          # применение миграций
make -f Makefile.prod compilemessages  # компиляция переводов
make -f Makefile.prod collectstatic    # сборка статики
make -f Makefile.prod create-superuser # интерактивное создание администратора
```

Команды используют `.venv/bin/python`, без автоматической установки зависимостей
через uv. Другой интерпретатор можно указать как
`make -f Makefile.prod check PYTHON=/path/to/venv/bin/python`.
Все операции, кроме справки, отказываются выполняться при итоговом `DEBUG=True`.
Окружение и серверный `.env` должны быть подготовлены заранее. Команда `check`
считает предупреждения безопасности ошибками; исправьте настройки до деплоя.
Проверка `DEBUG=False` не определяет, к какой именно БД вы подключаетесь:
перед миграциями проверьте серверный `DATABASE_URL` и подготовьте резервную копию.

В этом файле нет запуска dev-сервера, управления dev-БД, сброса данных,
создания миграций или тестового администратора. PostgreSQL и Gunicorn запускаются
системными службами. `create-superuser` запрашивает пароль интерактивно.
Для `compilemessages` нужен gettext. CSS при необходимости соберите до
`collectstatic` (`npm ci`, затем `npm run css:build`); Node.js нужен в окружении
сборки CSS, а не для работы Django.

При подготовке архива для сервера включайте `Makefile.prod`, исключая локальный
`Makefile`, `scripts/dev_db.py`, `.local/` и локальный `.env`. Сам по себе новый
Makefile не меняет состав поставки: при Git checkout dev-файлы останутся
в репозитории. Отсутствие команд в Makefile не заменяет права пользователей ОС и БД.

### Первый администратор боевого сайта

Администратор сайта — **Django superuser**, учётная запись в базе приложения.
Она создаётся **вручную при первом деплое**: запуск Gunicorn, применение
миграций и наличие переменных `DJANGO_SUPERUSER_*` в `.env` сами по себе
администратора не создают. Успешный запуск приложения ещё не означает,
что в админку уже можно войти.

Тот, кто разворачивает сервер, должен выполнить этот шаг из корня проекта,
с тем же серверным окружением и `DATABASE_URL`, которые использует Gunicorn.
При `DJANGO_DEBUG=False` и после установки зависимостей:

```sh
make -f Makefile.prod migrate
make -f Makefile.prod create-superuser
```

Вторая команда запускает интерактивный `createsuperuser`: укажите логин,
email и собственный надёжный пароль (ввод пароля не отображается).
Это отдельная учётная запись: пользователь ОС, роль PostgreSQL и аккаунт
на сайте не заменяют её. Для выполнения команды нужны доступ к серверу
и подключение к боевой БД; знать внутреннее устройство Django не требуется.

После запуска сайта откройте `https://<домен-сайта>/admin/` и войдите
с созданными данными. Проверьте доступ к разделам наполнения контентом.
**Первый деплой считайте завершённым только после успешного входа в админку.**
Если сайт наполняет другой человек, передайте ему адрес админки и данные
входа по защищённому каналу.

При обновлении кода создавать аккаунт повторно не нужно: он сохраняется
в production-БД. Если пароль потерян, его можно сменить на сервере:

```sh
.venv/bin/python manage.py changepassword <логин>
```

Команду смены пароля также выполняйте с окружением боевого приложения.
Она не требует знания старого пароля. После смены проверьте вход в `/admin/`.

Переменные `DJANGO_SUPERUSER_USERNAME`, `DJANGO_SUPERUSER_EMAIL` и
`DJANGO_SUPERUSER_PASSWORD` из `.env.example` предназначены для локальной
команды `make create-test-admin` (`createsuperuser --noinput`). Это тестовые
данные, их нельзя использовать для боевого аккаунта. Для описанного выше
интерактивного создания production-администратора удалите эти переменные
из серверного `.env` и окружения: логин, email и пароль задаются вручную.
Изменение этих переменных не меняет пароль существующего пользователя.

### Запуск WSGI-сервера

Точка входа Django — `config.wsgi:application`. Базовая команда запуска
из корня проекта после установки зависимостей в `.venv` и подготовки
серверного `.env` или переменных окружения (см. выше):

```sh
.venv/bin/gunicorn config.wsgi:application
```

По умолчанию `DJANGO_SERVE_STATIC=True`: WhiteNoise раздаёт собранную статику
через Gunicorn, в том числе при `DJANGO_DEBUG=False`. Если на сервере `/static/`
обслуживает Nginx, задайте `DJANGO_SERVE_STATIC=False` в окружении службы
или серверном `.env` и перезапустите Gunicorn. Это отключает только
`WhiteNoiseMiddleware`; backend `CompressedManifestStaticFilesStorage`
остаётся включённым. Перед запуском и после обновления статики по-прежнему
выполняйте `collectstatic`.

Администратор настраивает адрес и порт или Unix-сокет, количество воркеров,
подключение Nginx, системную службу FreeBSD, автозапуск и перезапуск процесса.
Эти параметры задаются на сервере; отдельной команды запуска в Makefile нет.

## Логирование на сервере

Django выводит сообщения уровней `WARNING`, `ERROR` и `CRITICAL` в `stderr`
при любом значении `DJANGO_DEBUG`. Запись содержит время, уровень и имя логгера;
для исключений с переданной информацией об ошибке добавляется traceback.
Почтовый обработчик Django отключён: письма об ошибках не отправляются.
Приложение не создаёт файлы журналов. Локальный `runserver` сохраняет свой
стандартный журнал запросов.

Администратор сервера должен настроить сбор `stderr` процесса приложения,
место хранения, ограничение размера и количества архивов и ротацию журналов.
Например, можно хранить текущий файл и несколько архивов по 5–10 МБ.
Журналы веб-сервера и Gunicorn настраиваются и ротируются отдельно.

## Парсеры библиографических файлов

`publications/importers.py` разбирает ровно одну публикацию из BibTeX или RIS.
В админке на странице добавления публикации доступен блок «Заполнить из файла».
Выберите `.bib` или `.ris` и нажмите «Прочитать файл»: поля заполнятся без
сохранения. Проверьте предупреждения, выберите сотрудников и направления,
затем прикрепите вложения и сохраните карточку. При повторном импорте
браузер запрашивает подтверждение замены введённых данных; выбранные вложения
нужно добавить заново. Ошибка чтения сохраняет значения основной формы.

При найденном дубле показываются ссылки на существующие карточки. Для
сохранения отдельной записи нужно явно отметить подтверждение; проверка
повторяется при сохранении, включая редактирование (текущая карточка исключается).

Сам парсер не сохраняет записи,
не загружает вложения и не обращается к внешним API.

```python
from publications.importers import parse_publication, find_duplicates

result = parse_publication(uploaded_file)  # Django UploadedFile, UTF-8, до 2 МБ
# Либо parse_publication(text_or_bytes, format='bibtex') / format='ris'.
initial = result.data             # Значения полей Publication для формы
errors = result.errors           # Ошибки полей, которые нужно исправить
warnings = result.warnings       # Неизвестный тип и неперенесённые поля
unmapped = result.unmapped_fields  # Неперенесённые поля с исходными значениями
matches = find_duplicates(result)  # DuplicateMatch(publication, reason)
```

Пустой, повреждённый файл или несколько записей вызывают
`PublicationImportError`. Недостающие обязательные значения остаются в
`result.errors`: форму можно заполнить вручную. Неизвестный тип заменяется
на «Другое» с предупреждением. Публикация всегда предлагается как черновик.

Поиск дублей сравнивает нормализованный DOI, а при отсутствии DOI во входных
данных — название без различий регистра, пробелов и пунктуации вместе с годом.
Он включает неопубликованные карточки. Для редактирования можно передать
`exclude_pk`, для ограничения области поиска — `queryset`. Это кандидаты для
проверки человеком; записи не изменяются. При подключении к админке проверку
следует выполнять и перед сохранением.

Тесты: `uv run python manage.py test publications`.

## Учёные степени, звания и статус сотрудников

В админке карточки сотрудника доступны отдельные поля «Учёная степень»
(кандидат или доктор наук с указанием отрасли), «Учёное звание» (доцент или профессор) и
«Действующий сотрудник». Степень и звание необязательны и показываются
в списке сотрудников и личной карточке, если заполнены. Эти поля редактируются
через админку, а не через форму самостоятельного редактирования карточки.

После обновления выполните `make migrate`. Для существующих карточек степень
и звание остаются пустыми; все сотрудники по умолчанию считаются действующими.
Проверьте этот статус у бывших сотрудников. Он независим от публикации карточки
и активности аккаунта; пока статус не меняет состав публичного списка.
Для будущей статистики действующий состав выбирается через
`Employee.objects.current()`, только опубликованный — через
`Employee.objects.current().published()`. На странице истории статистика рассчитывается по всем действующим сотрудникам,
включая неопубликованные карточки. Научные сотрудники определяются по научной
должности; кандидаты и доктора наук считаются только среди них.

Степени и звания отображаются сокращённо: к.х.н., к.ф.-м.н., к.б.н.,
д.х.н., д.ф.-м.н., проф., доц. Ранее сохранённые степени без отрасли остаются
как «к.н. (отрасль не указана)» и «д.н. (отрасль не указана)» — уточните их
в админке. Для подсчёта по уровню степени используйте фильтр
`academic_degree__in=AcademicDegree.candidates()` или
`academic_degree__in=AcademicDegree.doctors()` из `users.models`.


## Студенты и аспиранты лаборатории

Все участники хранятся в `users.Employee` (в админке — «Карточки участников
лаборатории»). Статус обучения `education_status` необязателен: пустое значение,
«Студент» или «Аспирант». Он независим от научной и инженерной должности.
Поле `study_year` — необязательный положительный номер курса только для студентов;
курс обновляется вручную. При смене статуса на аспиранта или пустое значение
нужно очистить курс. Статус обучения и курс редактирует администратор; владелец
карточки по-прежнему меняет только ФИО, фото и описание.

На странице «Сотрудники» опубликованные карточки разбиты на сотрудников,
аспирантов и студентов. При наличии любой должности человек показан один раз
в разделе сотрудников с дополнительной подписью об обучении. Без должности
и с пустым статусом человек также остаётся в разделе сотрудников. Пустые разделы
скрыты. В разделах обучающихся используется алфавитная сортировка.
Все опубликованные карточки с выключенным признаком «Действующий участник»
показываются только в последнем разделе «Сотрудники и студенты лаборатории
в прошлом», по алфавиту, независимо от должностей и статуса обучения.
Статистика истории учитывает действующих участников без статуса обучения
и обучающихся с должностью, включая неопубликованные карточки.

Аккаунт необязателен. Для доступа студента или аспиранта к внутренним материалам
создайте аккаунт с ролью «Сотрудник»; при необходимости привяжите его к карточке.
Публикация карточки, статус обучения и признак действующего участника сами
по себе не дают и не отзывают доступ. Для его отзыва можно отключить аккаунт.
Роль «Сотрудник» даёт доступ к внутренним материалам, но не вход в админку.
Миграция `0006` снимает `is_staff` у существующих пользователей группы
«Сотрудники», кроме суперпользователей. Обратная миграция автоматически
не восстанавливает этот флаг. Роль «Администратор» сохраняет полный доступ.

После обновления выполните `python manage.py migrate`.

## Галерея

Публичная страница `/gallery/` доступна из обычного и мобильного меню.
Добавляйте снимки в админке: «Контент сайта» → «Фотографии галереи».
Укажите фотографию, подпись и **год съёмки**, затем включите «Показывать на сайте».
Меньшее значение поля «Порядок» выводится раньше; при равенстве сначала идут
более новые годы и записи. На странице показывается до 24 фотографий.

Принимаются JPEG, PNG и WebP до 20 МБ и 40 мегапикселей. Оригиналы сохраняются
в `MEDIA_ROOT/gallery/<год съёмки>/`, уменьшенные JPEG-копии — в подкаталоге
`thumbnails/`. Имена файлов генерируются автоматически. Изменение года в карточке
не перемещает существующие файлы; новая загрузка использует указанный год.
При замене фотографии или удалении записи, в том числе массовом через админку,
прежние файлы удаляются после успешного завершения транзакции.

Скрытие фотографии убирает её из галереи, но не закрывает прямую ссылку на файл:
все файлы галереи публичные. На сервере настройте раздачу `/media/` веб-сервером,
храните `MEDIA_ROOT` на постоянном диске/томе и резервируйте вместе с базой данных.
Для включения раздела после обновления выполните `make migrate`.


## Языки интерфейса

Русский — основной язык: существующие адреса сохраняются (`/`, `/science/`).
Английская версия доступна под `/en/` (`/en/`, `/en/science/`).
Язык публичной страницы определяется адресом; русский остаётся по умолчанию
независимо от языка браузера. Переключатель RU / EN в шапке доступен
на компьютере и телефоне и сохраняет текущую страницу и параметры запроса.
Админка доступна по прежнему адресу `/admin/`.

Строки интерфейса помечены `translate` / `blocktranslate` в шаблонах
и `gettext_lazy` в Python. Английский каталог: `locale/en/LC_MESSAGES/django.po`.
Для обновления переводов установите системный GNU gettext (`apt install gettext`),
выполните `make messages`, заполните `msgstr` в каталоге и запустите
`make compilemessages`. Файл `django.mo` включён в репозиторий для локального
запуска; после изменения каталога обновляйте его вместе с `.po`.
На сервере используйте `make -f Makefile.prod compilemessages`.
Перезапустите сервер после обновления переводов.

На этом этапе переведён общий интерфейс: шапка, подвал, главная, вход,
навигация, подписи разделов, поиск публикаций и пагинация. Контент из базы переводится отдельно от интерфейса (см. ниже).
Страница History и вводный текст раздела «Студентам» переведены через gettext.
Для названий документов предусмотрены необязательные английские поля;
если перевод не заполнен, показывается исходное название.


### Переводы контента в базе

Для научных направлений, участников лаборатории и объявлений добавлены
необязательные английские поля:

- `ResearchDirection`: `name_en`, `description_en`;
- `Employee`: `last_name_en`, `first_name_en`, `mid_name_en`, `bio_en`;
- `Announcement`: `title_en`, `text_en`.

Существующие поля остаются русскими. В админке тексты сгруппированы
в разделы «Русский текст» и «English»; поиск поддерживает оба языка.
Английское написание имён вводите вручную, как в публикациях сотрудника.
На данном этапе английские поля редактируются через админку; публичная
форма редактирования своей карточки по-прежнему меняет русские поля.

Сайт выбирает содержимое по текущему языку через свойства `localized_*`.
Если английское поле пустое или содержит только пробелы, выводится русское
значение этого поля. Поля независимы: можно перевести название, оставив
описание на русском. Для ФИО применяется то же правило к каждой части имени.
Переводы используются на главной, страницах участников и направлений,
в связанных ссылках и списках выбора фильтра публикаций. Slug, адреса, связи,
правила публикации и исходные библиографические данные не изменяются.
Порядок записей по-прежнему определяется существующими правилами.

После обновления выполните `make migrate` (миграции `core.0004`,
`users.0007`, `research.0010`). Существующие записи сохраняются, английские
поля изначально пустые. Для перевода этих записей `makemessages` и
`compilemessages` не нужны — изменения в админке сразу видны на сайте.


### Остальные переводы контента

Английские поля также доступны для следующих данных:

- Проекты: название, аннотация, источник финансирования, заказчик, программа;
  внешние участники: ФИО и организация.
- Публикации: `note_en` (примечание лаборатории) и `authors_text_en`
  (английское написание авторов). Поиск учитывает оба списка авторов.
  Название, журнал, аннотация статьи, DOI и прочие метаданные остаются исходными.
- Галерея: `caption_en`, используемое также в описании изображения и ссылки.
- Учебные материалы: описания, краткие описания лабораторных работ, оборудование,
  описания курсов, примечания лектора и подписи вложений.
- Диссертации: автор, специальность, руководители; дипломы: внешние руководители.

Все английские поля необязательны и редактируются в админке. При отсутствии
перевода выводится русское значение. Названия статей, диссертаций, дипломов,
курсовых, лабораторных работ и учебных документов не переводятся автоматически.
Подпись вложения лекции можно перевести отдельно от названия самого документа.

Фиксированные названия и сокращения должностей, учебных статусов, степеней,
званий и типов публикаций/работ переведены через gettext. Значения enum в базе
не изменились; отдельных полей для этих справочников не требуется.

После обновления выполните `make migrate` (добавлены миграции `core.0005`,
`research.0011`, `publications.0007`, `education.0006`) и обновите скомпилированный
каталог, если редактировали `.po`. Готовый `.mo` включён в репозиторий.


### Английские названия работ и учебных материалов

Необязательное поле `title_en` есть у диссертаций, дипломов, лабораторных
работ, учебных материалов, курсов и лекций. В админке оно подписано
«Название — EN»; у лекций доступно также в списке внутри курса.
На сайте названия выводятся через `localized_title`, в том числе в заголовке
страницы курса, списке курсов и названиях отдельных лекций.
У научных проектов аналогичное поле — `name_en` в разделе «English».
Переводы названий заполняются редактором вручную, без автоматического перевода.

Темы на странице «Дипломные и курсовые работы» теперь хранятся в модели
`StudentWorkTopic` («Темы дипломных и курсовых работ» в админке).
Можно менять русское и английское названия, вид работы, раздел, порядок
и видимость. Миграция переносит все 40 прежних тем из HTML с сохранением
их порядка и разделов; английские названия изначально пустые.
Это архив тем; отдельные записи защищённых дипломов остаются в разделе
«Выпускные квалификационные работы».

Английские должности выводятся полностью: `Senior Researcher`,
`Leading Engineer`, `Head of the Laboratory`. Обозначения степеней
`PhD in Chemistry`, `D.Sc. in Chemistry` и полные названия должностей
следуют формулировкам [английской версии старого сайта](https://rad.chem.msu.ru/wordpress/?page_id=390&lang=en)
и карточек сотрудников. Русские сокращения и значения enum в базе сохранены.

После обновления выполните `make migrate`: новые миграции `research.0012`,
`education.0007` и `education.0008`. Обновлённый `.mo` включён в репозиторий.

| Настройка | По умолчанию | Содержимое | Кто отдаёт |
| --- | --- | --- | --- |
| `STATIC_ROOT` | `staticfiles/` в корне проекта | Собранные CSS, JS, изображения интерфейса и статика админки | Nginx; без него настроен WhiteNoise |
| `MEDIA_ROOT` | `media/` в корне проекта | Только публичные загрузки: фотографии сотрудников и галерея | Nginx |
| `PRIVATE_PUBLICATIONS_ROOT` | `private_publications/` в корне проекта | Вложения публикаций, лекций, диссертаций, ВКР и **все** файлы `TeachingMaterial` | Django через обработчики скачивания |

У учебных материалов даже общедоступные файлы находятся в закрытом хранилище:
Django проверяет публикацию и уровень доступа при каждом скачивании. Изменение
«Для всех» на «Только для сотрудников» не требует перемещения файла. Ссылки
на файл материала строятся через `get_download_url()` или маршрут
`education:download_material`, а не через `/media/`.
HTML-шаблоны остаются частью кода приложения: Django формирует из них страницы;
Nginx не должен публиковать каталоги шаблонов.

На сервере задайте абсолютные пути в окружении службы и команд управления
или серверном `.env`, например (пути внутри Jail):

```dotenv
STATIC_ROOT=/var/www/lhec/staticfiles
MEDIA_ROOT=/var/db/lhec/media
PRIVATE_PUBLICATIONS_ROOT=/var/db/lhec/private
```

Каталоги загрузок должны сохраняться при обновлении кода. Пользователю Django
нужны чтение и запись в оба хранилища загрузок. Пользователю Nginx нужны только
чтение публичного `MEDIA_ROOT` и собранного `STATIC_ROOT`, а также проход по
родительским каталогам. Закрытое хранилище не публикуйте через `alias` или `root`.
Резервируйте БД и оба хранилища загрузок согласованно. Статика восстанавливается
сборкой: при изменении CSS выполните `npm ci` и `npm run css:build`, затем
`make -f Makefile.prod collectstatic`. Пользователю сборки нужна запись в
`STATIC_ROOT`; работающему приложению достаточно чтения этого каталога.

### Переход с прежнего хранения учебных материалов

Ранее `TeachingMaterial` сохранял файлы в `MEDIA_ROOT/education/materials/`,
в том числе внутренние материалы. **До завершения переноса не включайте прямую
раздачу `/media/`.** На время перехода остановите приложение и загрузку файлов,
сделайте резервную копию БД и каталогов. Затем:

1. Настройте постоянные хранилища. Если меняете пути, перенесите прежнее содержимое
   `media/` и `private_publications/` в соответствующие новые каталоги с сохранением
   вложенных путей. Не удаляйте прежние каталоги до проверки результата.
2. Примените `make -f Makefile.prod migrate` (миграция `education.0009` меняет
   хранилище поля, но сама файлы не переносит).
3. Выполните проверку, затем перенос. `--source-root` — абсолютный путь к каталогу
   media, где сейчас находятся старые файлы учебных материалов:

   ```sh
   .venv/bin/python manage.py move_teaching_materials --source-root /var/db/lhec/media --dry-run
   .venv/bin/python manage.py move_teaching_materials --source-root /var/db/lhec/media
   ```

Команда сохраняет имена файлов и ссылки в БД, проверяет копию перед удалением
исходника и допускает повторный запуск после частичного переноса. При конфликте
содержимого или отсутствии файла в обоих каталогах она останавливается с ошибкой.
`--dry-run` не изменяет файлы. Запускайте команду без параллельных загрузок.
Она переносит только файлы, на которые ссылаются записи `TeachingMaterial`:
проверьте оставшиеся файлы в `media/education/materials/` и уберите весь этот
старый подкаталог из публичного дерева после сверки с резервной копией.
Если исходных копий media несколько, очистите все каталоги, доступные веб-серверу.
На новой установке без старых файлов этот перенос не требуется.

После проверки скачивания публичного материала, отказа анонимному посетителю
для внутреннего и доступности его сотруднику можно включить раздачу Nginx.

### Nginx

В существующий `server` добавьте (пути должны соответствовать настройкам выше
и быть видны процессу Nginx; если он вне Jail, укажите пути с его стороны):

```nginx
location ^~ /static/ {
    alias /var/www/lhec/staticfiles/;
}

# Старое место учебных материалов больше не публикуется.
location ^~ /media/education/materials/ {
    return 404;
}

location ^~ /media/ {
    alias /var/db/lhec/media/;
    autoindex off;
    add_header X-Content-Type-Options nosniff;
}
```

Nginx отдаёт весь публичный `media/` без проверки пользователя. Закрытые файлы
обслуживает Django через `FileResponse` с проверками соответствующего раздела;
прямых публичных URL для закрытого каталога нет. WhiteNoise обслуживает только
статику, а не пользовательские загрузки. Локально при `DEBUG=True` публичные
media по-прежнему отдаёт Django.
